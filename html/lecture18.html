第 18 讲｜主动式 Agent

到目前为止，我们在课程中讨论的几乎所有 Agent——无论是问答助手、RAG 流水线，还是处理工单的编程 Agent——都遵循着同一种交互模式：被动响应式（Reactive）。如果你不向它发消息，它就永远安静地停在原地；只有当你明确敲下指令、点明要做什么，它才会启动循环去执行。

然而，真正得力的人类搭档绝不会事事等你开口下令。举两个日常场景：当你正在撰写季度总结文档、反复在邮件和表格之间切换查核数据时，一位默契的搭档会察觉你的意图，主动把最新一周的销售表格整理好放在手边；当你收到一封重要会议改期的邮件时，他会主动提醒你这与周四的航班冲突，并为你拟好改签建议草稿等你确认。

从“你问一句，我动一下（Reactive）”走向“理解你的上下文与长远目标，在恰当时机主动提供协助（Proactive）”，正是个人与企业 AI Agent 演进的下一个重大前沿。本讲将系统剖析主动式智能体（Proactive Agents）的核心技术体系：探讨如何从日常计算机交互中构建通用用户模型（General User Models, GUM）、如何进行下一步动作预测（Next Action Prediction）、剖析开源主动式个人 Agent（如 OpenClaw）的常驻架构，并深入研究持续观测带来的隐私信任挑战，以及决定“何时该主动出手、何时该安静等待”的混合主动权（Mixed Initiative）决策机制。

学习目标

  • 理解被动式智能体（Reactive Agents）与主动式智能体（Proactive Agents）的本质区别，认识主动性带来的生产力解放与干扰风险。
  • 掌握通用用户模型（General User Models, GUM）如何从多模态计算机交互日志中归纳用户的知识状态、偏好与当前目标。
  • 理解基于人机交互序列的下一步动作预测（Next Action Prediction），严格区分“预测用户下一步会做什么”与“Agent 获准替用户执行什么”。
  • 剖析开源常驻主动式 Agent（如 OpenClaw）的心跳唤醒（Heartbeat）、多通道网关与夜间记忆整理机制，掌握混合主动权（Mixed Initiative）的效用—打扰权衡与隐私边界设计。

知识讲解

1. 从 reactive 到 proactive

前 17 讲介绍的 Agent 大多停留在“你发指令、它再干活”的被动模式。本节将解答两个核心问题：为什么仅靠被动响应不够用，以及一套真正能主动帮忙的 Agent 需要具备哪些底层技术组件（用户理解、动作预测与常驻运行架构）。

Reactive 与 proactive

将响应式 Agent 与主动式 Agent 放在系统层面对比，两者的触发机制与认知负担截然不同：

维度被动响应式智能体（Reactive Agents）主动式智能体（Proactive Agents）
触发起点仅由用户的显式指令（Explicit User Prompt）触发由环境事件、时间周期、上下文状态变化或观测到的用户行为流自主触发
意图发现责任完全落在人类用户肩上（用户必须自己发现问题并把需求组织成清晰的提示词）由 Agent 与用户分担（Agent 持续感知上下文，识别潜在需求、冲突或可自动化的重复劳动）
主要失败模式答非所问、工具调用失败、执行超时误触发打扰（False-positive Interruption）、自作主张引发错误副作用、过度窥探造成隐私不安
核心评测指标给定指令下的任务完成率（Pass Rate）、成本与延迟建议采纳率、为用户节省的操作步数、打扰率（Interruption Rate）与撤销成本

为什么在很多真实办公场景下，仅靠 Reactive 模式是远远不够的？当人类用户专注手头工作时，往往面临三重现实障碍：

  1. 不知道可以自动化：用户没意识到某件繁琐重复的小事，其实完全可以交给 Agent 顺手处理；
  2. 提示规范开销（Prompting Overhead）过高：有时候把复杂的前因后果、文件位置和格式要求用文字敲成提示词讲给 AI 听，花的时间甚至比自己动手干完还要长；
  3. 盲区事件无从提问：面对日程冲突、后台系统报警或即将到期的截止日，用户自己根本还没注意到异常发生，自然不可能主动去问 AI。

General User Models（GUM）

要让一个 Agent 能够恰到好处地主动帮忙，前提是它必须先真正“懂你”——知道你正在忙什么项目、习惯什么样的工具流程、认识哪些合作者、有哪些未完成的待办事项。

斯坦福团队提出的通用用户模型（General User Models, GUM, Shaikh et al., 2025，《Creating General User Models from Computer Use》），开创了从日常多模态计算机使用行为中自动构建结构化用户表征的新范式。你可以把它理解成给 AI 建一本“持续更新、带证据来源的动态用户档案”，其运转分为三步：

  1. 多源交互观测（Multimodal Computer Use Observation）：系统在本地受控环境下，持续观察用户在操作系统中的日常交互轨迹，包括屏幕截图变化、活跃窗口切换、文档编辑以及网页浏览记录。
  2. 结构化命题归纳与置信度更新（Propositional User State）：如果只是把几万张原始截图直接塞进向量库（用数值向量存图、按相似度检索的数据库），不仅占用空间大，检索时还容易充斥大量无关噪声。GUM 的做法截然不同：它借助能够同时看懂图像和文字的视觉—语言模型，从交互流中持续提炼出一条条人类可读的结构化命题（Propositions）——例如“用户正在准备 CS329Z 的期中项目报告，重点关注 RAG 评估指标”，或“用户习惯使用 uv 而非 pip 管理 Python 环境”。同时，系统会为每条命题维护三项关键元数据：置信度（有多确定）、证据来源（从哪几次操作推断出来的）以及时效衰减（随着时间推移，旧习惯或已完成项目的权重会自动降低，防止画像僵化）。
  3. 跨应用泛化赋能：一旦建立起动态更新的 GUM，任何下游应用或 Agent 在启动时都无需用户从零交代背景。它们可以直接查询 GUM 获取高精度的个性化上下文，不仅能自动补全模糊指令里的指代（比如你说“把那份报告发给组员”，它知道是哪份报告、发给谁），还能主动发现跨应用的工作流衔接机会。

Next Action Prediction

有了对用户当前状态的理解，主动式 Agent 面临的下一个核心计算问题是下一步动作预测（Next Action Prediction, Shaikh et al., 2026，《Learning Next Action Predictors from Human-Computer Interaction》）。用序列建模的视角来看，给定用户过去一段时间的交互历史 (s1,a1,s2,a2,…,st)（其中 sk 代表第 k 步的界面状态，ak 代表用户的操作动作），模型需要预测用户接下来最可能执行的操作 at+1，或者更高层次的任务意图。

为了看清“预测”和“真正动手”之间的边界，我们来看本版教学示例：用户正把邮件里的 10 个日期逐个录入表格，已经填好了两行。模型观察到这个重复模式，预测第三行大概率也会继续填日期。注意，这里模型给出的仅仅是一个意图先验（Intent Prior）——也就是“在当前线索下，用户接下来有多大可能想干这件事”的概率判断。

仅有意图先验还远远不够。真正决定助手“要不要出手、怎么出手”的，是上层的主动决策策略（Initiative Policy）。它必须在行动前额外核查两件事：第一，用户此前授予过哪些操作权限；第二，此时跳出来展示建议，节省的精力是否值得打断用户当前的专注。

容易混淆：预测准确率高，绝不等于自动获得了执行权限。在上述示例中，如果用户允许助手生成预览，助手就可以把余下 8 个日期排成待核对的草稿；但即便它把 8 个日期全部猜对，直接写入共享表格依然需要用户的明确授权。

开源主动个人 Agent

理解了“懂用户”和“猜动作”的算法原理后，工程上如何把这些能力落地成一个 7×24 小时在线的个人助手？在开源工程界，以 OpenClaw（Steinberger, 2025） 为代表的常驻型个人 Agent 展示了如何用简洁的工程组件搭起这套系统（我们在第 05 讲曾简要见过其身影）：

  1. 单一长驻网关进程（Long-lived Gateway）：传统的对话助手是“打开网页才启动、关掉页面就结束”的临时会话；而 OpenClaw 采用一个常驻后台的网关进程，就像一位 24 小时值班的前台，统一接管用户的多个消息通道（如 Telegram、Slack、邮件通知以及本地目录的文件变化监听）。
  2. 定时心跳检查（Scheduled Heartbeat Turns）：后台服务会按固定节奏自动“醒来”巡检——例如把自动化任务设为每 30 分钟检查一次已授权的数据源。工程设计上有一个极其重要的原则：“定期检查”和“对外通知”是两项完全独立的决定。如果本轮巡检发现没有值得提醒的新变化，系统应当返回 NO_REPLY，悄无声息地结束本轮检查，让用户安心继续工作。OpenClaw 定时检查与静默结果
  3. 基于文件的指令与记忆（File-based Identity & Sleep-time Consolidation）：与其把 Agent 的人设和记忆黑盒化地藏在数据库里，OpenClaw 选择用直观的纯文本 Markdown 文件来管理——例如用 AGENTS.md、SOUL.md、USER.md 与 MEMORY.md 分别记录行为约定、角色设定、用户信息和长期记忆，方便用户随时打开检查和手改。此外，系统还支持将夜间整理（Sleep-time Consolidation）作为一种定时调度选择，在用户休息时段自动把当天获准保留的零散信息提炼、去重并归档到长期记忆中。

2. 隐私、信任与 mixed initiative

上一节我们拆解了主动式 Agent 如何通过持续观测、意图预测与定时心跳运转起来。然而能力越强、看得越多，风险也随之放大：本节将解决主动式 Agent 落地时最棘手的两道关卡——如何守住隐私与信任底线，以及如何在“主动出手”和“安静等待”之间做出不令人反感的决策。

Privacy and trust

主动式 Agent 观测的屏幕与个人数据越全面，它触及的隐私与信任边界（Privacy and Trust Implications）就越敏感。工程落地中必须守住两条底线：

  • 持续观测的最小化与本地化原则：屏幕截图、键鼠记录与私人通信中混杂着大量高敏信息（如密码输入框、私人聊天、银行账单与医疗记录）。在设计类似 GUM 的持续观测系统时，应当建立三道防线：第一，在采集端支持应用级黑名单过滤，直接排除密码管理器、私人金融与医疗页面；第二，优先采用本地端侧模型，在设备本地把画面提炼成抽象命题后立即销毁原始截图，不留存冗余敏感画面；第三，严禁将未经脱敏的原始监测流直接上传至不可信的公共云端。
  • 可审计与可修正的透明度（Inspectability & Correctability）：黑盒式的“猜你心思”极易引发用户的失控感。用户必须能够随时打开查看“Agent 目前对我形成了哪些推断和记忆”，并能一键删除或纠正错误条目——比如当 Agent 误以为用户对某个临时帮朋友搜索的商品长期感兴趣时，用户能直接划掉该画像条目，且系统能确保旧推断立刻失效。这种可见、可改的透明机制，正是建立长期人机信任的基石。

Initiate vs wait

主动式 Agent 设计的最高艺术，在于处理混合主动权（Mixed Initiative，Horvitz, 1999 经典人机交互理论在 LLM 时代的延续）——也就是在每一个时刻，系统如何在“主动发起行动（Initiate）”、“礼貌询问或提供草稿（Suggest / Ask）”与“安静等待（Wait / Do Nothing）”之间做出最优抉择。

我们可以用一个简单的期望效用决策矩阵（Expected Utility）来把这种直觉量化，指导工程里的阈值设定。设 Agent 估计当前用户确实需要某项帮助的概率为 P(Need)：

  • 如果主动出手且猜对了，能为用户带来的净收益（如节省的时间和精力）为 Uhelp>0；
  • 如果主动出手但猜错了（误触发），给用户造成的打扰成本与撤销/清理代价为 Cinterrupt>0。

在这个简化模型里，我们把“安静等待”的净收益设为 0。对于一个已经获得用户授权的动作，采取它的期望净收益为：

E[Uact]=P(Need)⋅Uhelp−(1−P(Need))⋅Cinterrupt

当且仅当 E[Uact]>0，也就是满足：

P(Need)⋅Uhelp>(1−P(Need))⋅Cinterrupt

采取该动作的期望净收益才严格高于等待。把含 P(Need) 的项合并到左侧，可以进一步推导出一个非常直观的行动置信度门槛：

P(Need)>CinterruptUhelp+Cinterrupt

这个门槛公式揭示了两个关键工程直觉：第一，打扰代价 Cinterrupt 越高，出手门槛就越严苛——比如立刻弹窗打断用户写代码，代价很大，只有把握极高时才该弹；如果只是在后台悄悄准备好草稿，打扰代价几乎为零，哪怕把握没那么大也可以先备着。第二，如果要比较多个候选动作，必须分别估计各自对应的收益与代价——同一个提醒，是等用户打开日历时再展示，还是立刻弹窗，两者占用注意力的时机不同，代价自然不同。同时也要注意该模型的适用边界：它只用于权衡“已获授权动作”的出手时机；对于未授权、不可逆或涉及外部他人的操作，用户授权是硬前提，不能单靠 P(Need) 很高就直接越权执行。

为了让系统能根据风险与打扰成本灵活换挡，工程上通常采用渐进式的介入阶梯（Graduated Spectrum of Initiative）。本版用一个日历事件来直观演示这四个等级：假设明天的一场会议刚改期，和已有安排重叠。助手有权读取忙闲信息，也已经确认冲突；下面保持事件本身不变，只改变用户为这类事件设定的规则。

怎样科学地评测助手“打扰得合不合适”？ 工程上不能只凭感觉，需要建立包含正负样本的闭环评测流程：

  1. 构建标注基准：先让用户或标注者在真实事件流中事后判定哪些事件当时确实值得提醒，同时保留大量“本就应该保持安静”的日常样本（避免只测正例导致模型过度活跃）。
  2. 拆分核心指标：
    • 精确率（Precision）：在助手实际发出的所有提醒中，有多少比例确实值得发（精确率低，说明误打扰太多）；
    • 召回率（Recall）：在所有本该提醒的事件中，助手成功覆盖了多少比例（召回率低，说明漏报了重要事项）；
    • 建议采纳率（Adoption Rate）：应单独统计，因为有时用户完全认同这条提醒很有价值，只是出于个人习惯选择自己去处理，不能因此把有效提醒误判成失败。
  3. 拒绝后重放测试（Anti-Nagging Replay）：把用户已经明确拒绝或忽略的同一事件再次重放给系统，检验决策策略是否能记住用户反馈、按约定保持安静，避免反复弹窗骚扰。

  • 拓展阅读：Steinberger. "OpenClaw: Open-source proactive AI agent." (2025). 导读：推荐直接浏览仓库的架构文档与核心配置，重点看它的 Gateway 长驻网关、Heartbeat 定时轮询机制（特别是 NO_REPLY 静默协议），以及如何用 SOUL.md、USER.md、MEMORY.md 等纯文本 Markdown 文件清晰地管理常驻个人 Agent 的状态。

动手练习

  1. 设计四级混合主动权（Mixed Initiative）策略引擎：围绕日常个人办公场景构造 8 个事件快照（至少包含以下 4 个典型场景，其余 4 个可结合自己的工作流补充：① 收到一封明天的普通推广周报；② 收到一封要求周五前回复报销单的同事邮件；③ 检测到 15 分钟后有线上会议但尚未生成议程摘要；④ 用户刚刚在 2 分钟前点击拒绝了“自动整理桌面文件”的建议）。为每个事件明确判定应采取的介入等级（Level 0 静默 / Level 1 后台草稿 / Level 2 主动弹窗建议 / Level 3 自动执行），并结合本讲的授权边界、打扰成本、可逆性与时效紧迫度写出判断依据。
  2. 实现心跳检查与防重复打扰状态机：用你熟悉的语言（如 Python）编写一个模拟 heartbeat_check(events, memory) 的函数，体验“定期检查”与“对外通知”的分离设计：
    • 输入：events（当前轮询拉取到的事件列表，包含事件 ID、优先级、时间戳、内容摘要）与 memory（记录历史已提醒事件及提醒时间的持久化字典）。
    • 静默条件：当没有任何紧急新事件，或者某事件已在过去 24 小时内提醒过用户且没有实质性新变化时，函数必须严格返回 "NO_REPLY"。
    • 触发动作：当发现新的高优先级冲突时，先模拟调用只读工具准备好上下文草稿，再生成一条不超过 100 字的精简行动建议，并将该事件 ID 与当前时间戳写入 memory，确保下一轮心跳不会重复打扰。
