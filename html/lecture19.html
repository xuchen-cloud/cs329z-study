第 19 讲｜前沿与开放问题

走过前面十八讲，我们已经完整走通了现代 AI Agent 工程的核心主干：从基础模型解码、注意力机制、RAG 检索与工具协议，到编排框架、上下文管理、记忆架构、多智能体协作与系统优化，再到数据飞轮、基准设计、LLM 裁判、安全护栏以及编程与主动式 Agent。

作为全课程的收官之讲，我们将目光投向正在飞速演进的技术前沿（Frontiers）与尚未被彻底攻克的开放研究与工程难题（Open Problems）。当 Agent 的感知从纯文本扩展到多模态屏幕与真实网页，当应用领域深入到自动化科学发现（Science Agents），当任务周期从几分钟拉长到跨数天连续运行，当原型系统真正走向日均百万次调用的生产环境——我们会面临哪些全新的架构挑战？本讲将系统梳理多模态与计算机操作 Agent（Web & Computer Use）、科学智能体、超长周期架构、生产级可观测性与成本治理（Tracing、Monitoring、Cost Management），以及横亘在可靠性、可扩展性与可解释性（Reliability、Scalability、Interpretability）面前的核心开放问题。

学习目标

  • 理解多模态智能体（Multimodal Agents）、网页交互与真实计算机操作智能体（Web Agents & Computer Use，如 WebShop、OSWorld）的感知—动作空间与评测挑战。
  • 理解科学智能体（Science Agents）与超长周期运行架构（Long-running Architectures）的设计边界与状态一致性要求。
  • 掌握生产级 Agent 系统的三大运维支柱：全链路追踪（Tracing）、持续监控告警（Monitoring） 与 多维成本治理（Cost Management）。
  • 深入思考并能够将 Agent 领域的三大开放挑战——长程可靠性（Reliability）、并发可扩展性（Scalability） 与 行为可解释性（Interpretability） 转化为具体的研究与工程实验。

知识讲解

1. 能力与环境的扩展

前十八讲里，我们打造的 Agent 大多生活在一个相对“干净”的纯文本世界：调用结构化工具、读写代码文件、在几分钟内结束一次会话。本节要解决的问题是：当 Agent 走出纯文本舒适区，开始看懂图形界面、操作真实电脑、做科研实验，甚至跨越多天持续工作时，感知、执行和状态管理会冒出哪些全新的难题？

Multimodal agents

在前几讲中，Agent 与环境交互的主要媒介是结构化文本（如 JSON 工具返回、文件内容或命令行输出）。然而，人类数字世界中还有海量软件与信息从未暴露过干净的命令行或 API 接口——比如复杂的图形设计软件、带图表的 PDF 财报、电子表格界面、视频流以及物理世界的摄像头画面。

多模态智能体（Multimodal Agents） 正是为了突破这一限制，它可以直接根据图像、音频等非文本输入来判断并采取行动。但引入视觉等模态后，排错难度瞬间升级：一次答错既可能是“没看清屏幕”（感知错误），也可能是“看清了但算错/想错了”（推理错误），两者在最终结果上往往混在一起，难以一眼分清——这就是感知与推理纠缠（Perception-Reasoning Entanglement）。

来看一个教学示例：任务要求从图表中选出“增长率较低的地区”。屏幕上清楚地标着「华东 2%、华南 8%」，助手却选了华南。光看最终答案，我们无法判断问题出在哪里；下面两份可能的运行记录（数字均为教学假设），展示了截然不同的排查方向：

因此，在评测多模态 Agent 时，不能只看最终正确率，而应把链路拆开，分别记录「地区和数值的配对正确率」与「给定正确配对时，选中较低值的比例」。只有把感知得分和推理得分拆开看，才能明确下一次实验该改视觉模块还是推理逻辑。

Web agents and computer use

多模态感知与底层动作空间结合的最重要战场，是 网页智能体（Web Agents，如 WebShop, Yao et al., 2022） 与 通用计算机操作智能体（Computer Use Agents，如 OSWorld, Xie et al., 2024）。

在这类环境中，Agent 拿到的观测（Observation）不再是简洁的 API 返回值，而是浏览器的 DOM 树（网页的 HTML 结构树）、可访问性树（Accessibility Tree，操作系统为屏幕阅读器等无障碍工具提供的控件层级描述）或高分辨率桌面屏幕截图；而它的动作空间（Action Space）则是模拟真人的底层操作：鼠标点击 click(x, y)、拖拽、键盘输入 type(text) 与快捷键组合。这种“像人一样操作电脑”的设定带来了三项严峻挑战：

  1. 动态异步与不可靠界面：真实网页和桌面应用充满了异步加载动画、悬浮菜单、广告弹窗与隐藏状态。点击之后页面未必立即就绪，甚至在 Agent 思考的零点几秒里，列表顺序或按钮位置就已经悄悄变了。
  2. 混合表征取舍：只看纯 DOM 树，往往要面对数万行充斥着混淆类名的 HTML 噪音，既费 Token 又容易迷失；只看纯屏幕截图，又很难精确定位微小图标的像素坐标。目前的主流探索方向是混合感知——把精简后的可访问性树、标记框叠加（Set-of-Marks，简称 SoM，即先在截图上的可点击控件旁画上带编号的方框，让模型直接报编号而非猜像素坐标）与原始视觉截图结合起来，取长补短。
  3. 基于真实系统状态的评测（Execution-based Outcome Evaluation）：正如 OSWorld 在 Ubuntu、Windows 和 macOS 真实虚拟机环境中所展示的那样，判断一个跨应用桌面任务（例如“把邮件附件里的音频去噪后插入演示文稿第 3 页”）是否完成，绝不能靠看最后一张屏幕截图长什么样。必须在虚拟机内部运行后置检查脚本，直接核验生成的文件内容、应用配置数据库与系统状态，确保结果在底层真正落盘且符合要求。

故障最早出现在哪一帧？ 接着上面的教学例子，假设助手已经正确选定「华东」，现在要把它的图表插入周报第 3 页。最后一张截图里，第 3 页确实有图，表面看任务似乎成功了。但只要沿着下面三条记录回溯，就能精准揪出图表从哪一刻开始与目标不符：

时刻可核对的证据能判断什么
选择前可访问性树显示第 2 行「华东」，第 3 行「华南」。助手选定「华东」，记下第 2 行坐标。起初识别出的目标正确。
点击时列表刚按更新时间重新排序，当前第 2 行显示「华南」。助手仍点击原坐标。先前的坐标已经失效。临点击时需重新读取当前行的名称。
保存后独立检查打开保存的周报，读出第 3 页图表的数据区域为「华南」。插图动作成功，交付内容错误。应同时核对页码和图表数据。

这个例子生动说明了为什么异步界面和真实状态核验如此关键：哪怕起初识别对了、最后也成功插了图，中间一次界面重排就足以让旧坐标点错对象。

Science agents

另一个令人振奋的前沿方向是 科学发现智能体（Science Agents）——将 Agent 应用于文献调研、提出科学假设、编写实验代码、调度实验室自动化设备或分子动力学模拟，并分析实验结果来不断修正假设。

在构建和评估 Science Agents 时，最核心的科学纪律是：严格区分“生成了一段听起来像科研论文的假说文本”与“通过严谨的对照实验与统计检验真正证实了新发现”。模型天生擅长写出流畅、极具说服力的学术腔，这反而让它在开放探索中极易犯下科研大忌：

  • 挑拣数据（Cherry-picking）：只挑选符合自己预设假说的数据点画图，忽略或隐瞒反例；
  • 隐性过拟合：在测试集上反复调参、试遍几十种方法后挑出误差最低的一个，把偶然的运气当成普适规律；
  • 误把 Bug 当突破：把代码逻辑错误或数据泄露产生的异常数值，当成重大科学发现大书特书。

因此，可靠的科学 Agent 不能只靠“自由发挥”，必须在架构中内置强制的基线对照（和公认的基准方法同台竞技）、消融验证（去掉某个改动看效果是否真的变差，确认增益来源）以及独立复现沙箱（在隔离环境中重新跑通全流程，确认结果可复现）。

Long-running architectures

当任务跨度从几分钟的单次会话，延伸到持续数天甚至数周的 超长周期架构（Long-running Agent Architectures） 时，系统设计的核心就从“单次提示词技巧”全面转向了分布式状态工程。想象一下，如果一个 Agent 要花三天重构一个大型代码库，期间可能遇到网络中断、进程重启、上下文窗口装满等各种意外，系统必须做到“随时能停、停完能接、接上不乱”：

  • 状态检查点与增量契约（Checkpointing & Incremental Contracts）：就像玩长篇游戏需要定时存档一样，系统必须借助像 Temporal 这样的持久化编排引擎（能够自动记录工作流执行进度、崩溃后断点续传的框架），或者采用第 17 讲讨论的基于文件系统任务账本（feature_list.json + Git commits）的交接协议。这样无论何时发生进程重启或上下文窗口刷新，新的执行轮次都能从最近一个已验证的干净检查点无缝恢复。
  • 防范“状态腐化持久化”：持久化机制是一把双刃剑——它能稳稳保住正确进度，但如果不加甄别地把中间结果存盘，也会把早期某一步隐蔽的错误假设永久固化下来，导致后续几十步都在错误的地基上越走越偏。因此，每次将阶段性状态写入长期检查点之前，都应当设置一道确定性的验证门禁（Verification Gate）（如跑通单元测试、校验数据版本与格式约束），只有通过检查的产物才允许“盖章入库”。

2. 生产与开放问题

上一节我们看到了 Agent 在多模态、桌面操作、科研探索与超长周期上的能力跃迁。然而，让一个 Agent 在演示视频或基准测试里跑通是一回事，让它变成每天稳定服务成千上万用户的线上系统则是另一回事。本节要解决两个递进的问题：第一，如何用追踪、监控与成本治理三大支柱把 Agent 稳稳托在生产环境里；第二，当工程手段做到位后，整个领域还剩下哪三座尚未被彻底攻克的开放大山？

当一个 Agent 从能跑通基准测试的原型变成每天服务成千上万用户的生产系统时，工程师必须构建起支撑线上平稳运行的运维铁三角：追踪（Tracing）、监控（Monitoring）与成本治理（Cost Management）。

Tracing

全链路追踪（Tracing） 解决的是微观单点排错问题：当线上发生故障时，我们需要快速回答“昨天下午 3 点 12 分那位用户的请求到底死在了哪一步？”。

普通网页后端的调用链路相对固定，但 Agent 的执行路径是动态生成的——模型临时决定调几次工具、派几个子 Agent，每次请求都不一样。因此，生产级 Tracing 需要以分布式调用链（Trace ID → Spans）的形式来记录：可以简单把 Trace ID 理解成一次完整用户请求的“快递总单号”，而每个 Span 则是中间经过的“每一站扫描记录”。通过把总单号下的所有站点串起来，系统能关联记录一次任务中跨多个模型、子 Agent、MCP 工具服务与数据库查询的完整输入输出、耗时分布、重试原因与版本号。同时，为了守住安全底线，所有日志在落盘前必须自动脱敏个人隐私与密钥字段。

Monitoring

持续监控告警（Monitoring） 与 Tracing 形成互补：Tracing 用于微观的“事后尸检与单点排错”，而 Monitoring 则用于宏观把握整个系统的健康脉搏，在大量用户受影响前及时拉响警报。

除了传统的服务端系统指标——如每秒查询数（QPS）、延迟分位数 P50/P99（分别代表 50% 和 99% 的请求都在该耗时内完成，P99 专门用来盯住最慢的那 1% 长尾体验）以及 HTTP 5xx 错误率——Agent 生产监控还必须追踪专门的智能体健康度指标：

  • 异常终止分布：超出最大轮数（max_turns）、触发连续格式错误（malformed）或触发拒绝规则（deny_rules）的请求占比是否突然飙升；
  • 工具循环异味：单个会话平均调用工具的次数、重复调用同一工具的频率是否发生漂移（这往往意味着 Agent 陷入了死循环或某个外部工具返回值变了）；
  • 在线抽样评估（Online Shadow Evals）：线上用户请求没有现成的“标准答案”，因此可以异步抽取一定比例的线上真实轨迹，交给自动化无参考评分器（Reference-free Judges，即不依赖标准答案、仅根据任务目标与过程规范来打分的评审模型）打分，第一时间感知上游基础模型更新或外部 API 变动引发的质量退化。

Cost management

多维成本治理（Cost Management） 之所以在 Agent 生产环境中尤为致命，是因为它打破了传统问答应用的成本规律：在单轮问答应用中，单次请求的 Token 消耗和成本基本是固定的；而在自主 Agent 中，成本具有高度的长尾不可预测性——一次正常请求可能只花 0.01 美元，而一次陷入死循环或反复读取超大文件的异常请求，可能瞬间烧掉几十美元！

为了既不把预算烧穿，又不牺牲核心任务效果，生产级成本治理需要在四个层面同时设防：

  1. 单会话与单用户硬预算熔断（Hard Budget Caps）：如同 HW1 中实现的累计 Token 与美元账本检查，在每次发起新调用前核算余额，一旦单次运行逼近上限立即安全熔断，防止单个异常会话拖垮整月账单；
  2. 最大化前缀缓存命中率（Prompt Cache Optimization）：大模型处理输入时，需要先把整段上下文计算一遍（即 Prefill 阶段），这是长上下文开销的大头。如果多轮对话开头的系统提示词、工具定义完全一致，推理引擎就可以直接复用之前算好的缓存（Prefix Cache）。因此要固定系统提示与工具定义顺序，并结合 Observation Masking（在不破坏前文前缀的前提下遮蔽过期的冗长工具输出）避免每轮重排前缀，从而将高频长上下文的 Prefill 成本降低一个数量级；
  3. 模型分级路由（Model Routing & Cascading）：好钢用在刀刃上——把复杂的任务规划和关键决策交给高阶大模型，而高频的上下文摘要压缩（aux_lm）、简单分类与格式提取，则分流给高性价比的轻量级模型，或经在线蒸馏微调的小模型；
  4. 绘制质量—成本帕累托前沿：所谓帕累托前沿，就是“在同等花销下能达到的最高质量，或在同等质量下所需的最低花销”所连成的最优边界。任何架构改进都不能只炫耀准确率涨了几个点，而必须同时汇报准确率变化与单任务平均美元成本变化，看它是否真正把系统推向了更优的前沿。

Reliability

搭好运维铁三角之后，我们把视线投向整个 AI Agent 领域的未来——有三座横亘在研究者与工程师面前的核心开放大山。第一座大山是 长程可靠性（Long-Horizon Reliability）：

  • 为什么当前最先进的模型能够在单步推理题上超越人类博士，却依然会在连续 50 步的平凡办公操作中以不低概率犯下低级失误？
  • 单步通过率怎样影响整条任务？ 背后的数学直觉其实非常残酷——误差会随步骤数指数级累积。在本版教学算例中，假设一条任务包含 20 个步骤，必须全部成功才算完成，且各步相互独立、每步通过率同为 98%，中间没有重试。那么整条任务一次完成的概率是 0.9820≈0.668，即约 67%。也就是说，哪怕每一步都高达 98 分，连走 20 步也有约三分之一的概率翻车！
  • 独立性假设的边界：真实世界往往比这个公式更复杂。如果所有步骤共享同一份可能过期的输入，各步的成败就会产生相关性（一错全错），此时仅靠“单步平均通过率”便不足以推出整条任务的真实通过率。在工程实践中，一个务实的突破口是记录每次任务首次失败的位置，在最脆弱的节点加入可验证的中间状态（甚至局部重试），然后对比加入前后的整条完成率与额外成本。

Scalability

第二座大山是 系统可扩展性（Scalability）：

  • 当我们将单个 Agent 扩展为成百上千个并发运行的 Agent 集群时，很快会撞上一堵隐形墙：现有的工具生态与外部环境大多是按人类操作节奏设计的，并非为高并发智能体准备的。数据库锁竞争、外部 API 速率限制（Rate Limits）、沙箱容器启动开销都会瞬间爆发。同时，多个 Agent 之间还需要同步状态、避免重复劳动或互相覆盖修改，通信与同步开销可能随着 Agent 数量剧增，这就是多智能体系统中的“协调诅咒（Curse of Coordination）”，会迅速成为系统吞吐量的硬瓶颈。
  • 如何设计支持高并发乐观执行（先假设冲突较少而并发推进，提交前再校验冲突，而非全程加死锁排队）、自动冲突检测与亚线性通信开销（Agent 数量翻倍时，协调通信量增长得比翻倍慢得多）的多智能体基础设施，是系统工程界亟待突破的课题。

Interpretability

第三座大山是 行为可解释性与因果归因（Interpretability & Causal Attribution），它追问的核心问题是：到底哪些证据真正改变了 Agent 的动作？

在长程任务里，我们很容易落入一个直觉陷阱——直接问模型“你为什么这么做？”。但大量研究表明，模型对自己行为的自然语言解释，可能与实际驱动它做出决定的因素并不一致，这被称为不忠实的思维链（Unfaithful Chain-of-Thought）。换句话说，模型非常擅长“事后圆谎”：例如，助手可以在事后声称「页面刷新导致点错」，但这只是一句未经核实的辩解，我们必须调出操作记录，核对点击前列表到底有没有真的变过。

判断依据：想要验证某个因素是不是真正的原因，不能轻信模型的自述，而要做反事实重放（Counterfactual Replay）——通俗讲，就是“回到案发现场，只改一个条件，看结局变不变”。具体做法是：从点击前的同一状态分出两组，其他输入和配置完全保持一致，仅改变“列表是否重排”这一个变量，分别重复运行并比较选错图表的比例。两组差异越稳定，越能支持“重排确实影响了这一场景中的点击结果”。

回顾整门 CS329Z 课程，从第 01 讲画出的那张只有五个方框的 Agent 解剖图，到你亲手从零写出的每一步检索器、工具协议与运行底座，再到框架编排、记忆、多 Agent、优化、评测与安全——希望你带走的最核心收获不是某一个随时可能过时的 API 名称，而是这套以系统（System）、数据（Data）与评测（Evals）为支点，用严谨的实验证据拆解问题、权衡设计并掌控复杂性的工程思维。

动手练习

  1. 计算机操作任务（Computer Use）四元组与故障树设计：从 OSWorld 或你日常的桌面办公中挑选一个跨应用任务（例如：“打开本地 CSV 销售报表，找出本季度销售额下滑最严重的三个产品类别，生成一张柱状图保存为 PNG，并将其插入到周报 Markdown 文档的指定章节中”）。先写出该任务的四元组定义（目标/环境/观测空间/动作空间），再画出一棵故障诊断树，系统梳理三大层面的典型故障及对应的核验手段：感知层（看错坐标/列名）、执行层（路径/权限错误）与逻辑层（排序/聚合方向反了）。
  2. 反事实重放（Counterfactual Replay）归因实验：在你的课程项目或 HW1 Agent 的一条多步失败轨迹中，利用保存的追加式事件日志，从后往前定位到最早出现偏差的那一步。固定该步之前的所有状态，手动修改该步的单个上下文变量（例如删掉一条干扰文档片段，或补全一句工具报错提示），然后从该节点重新放行后续调用，多跑几次观察结果变化，用实测证据验证该变量是否为导致最终失败的真实因果根源。
