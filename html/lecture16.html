第 16 讲｜专题研讨：复合 Agent 系统架构复盘

在原课程安排中，本讲为面向业界前沿实践的机动客座讲座（Guest Lecture）。借着这个承上启下的节点，我们将前十五讲学过的零散技术串联成一张完整的工程全景图：把系统架构（System）、数据飞轮（Data）与评测与安全（Evals & Safety）三大支柱打通。

本讲旨在帮你梳理从零设计、调试到交付一个复合 Agent 系统时的核心决策清单与故障排查框架。打牢这套全局视角后，你就能更从容地衔接接下来最后三讲（编程 Agent、主动式 Agent 与前沿开放问题），并顺利推进期末系统交付。

学习目标

  • 将前十五讲的核心组件（模型底座、RAG 检索、工具协议、编排框架、上下文与记忆、多 Agent 协作、提示与权重优化、基准评测与安全护栏）整合为统一的工程全景图，理清各层之间的上下游依赖。
  • 掌握从零启动一个 Agent 工程项目时的五步架构选型决策矩阵，学会用真实失败证据驱动架构演进，避免过度设计与盲目堆砌复杂组件。
  • 建立跨层级的端到端系统故障诊断方法论，能够沿着完整执行日志由外向内快速定位并修复线上复杂轨迹中的瓶颈。

2. 三大支柱的工程闭环与选型矩阵

承接上一节的项目复盘定位，本节要解决的核心问题是：前十五讲介绍了这么多检索、记忆、编排和优化技术，从零搭建项目时究竟该先用哪些最简单的模块，又该凭什么证据才把系统变复杂？

哪一个变化值得多加一个组件？ 工程实践里的第一条原则，不是一上来就画出一张庞大的多 Agent 架构图，而是先跑通一条能完成基本任务的最小路径（也就是“基线”）。每当基线跑失败时，把当时的用户输入、工具回执和验收条件一起存下来，攒成一批可复现的失败样例。下表给出了五个关键的选型问题——任何升级方案是否真的有效，都应该放在同一批样例上与基线做公平对比。

待决定的事可运行的基线什么证据支持升级
谁决定下一步固定步骤用提示串联、路由或并行工作流下一步依赖尚未返回的线索，固定路径反复走不通，可比较 ReAct 等有步数上限的循环
怎样找到资料和工具先选一种适合语料的检索，工具职责清楚、接口一致（例如 MCP）候选缺相关文档时试 BM25 加向量检索与 RRF 融合；文档已在候选里却排太后时试 ColBERT 或 Cross-Encoder 重排；需要沿新线索再查时试有限跳数的 Agentic RAG
怎样保留任务状态保存原始事件日志，屏蔽过长的旧工具输出，保留可复用的上下文前缀超出窗口预算时试结构化压缩；确有跨会话需求时再比较 Mem0、MemGPT 或技能文件
工作该由几个 Agent 完成先记录强单 Agent 的质量、成本和耗时子任务确可并行或确需隔离上下文，再测试协调者与多个工作者；可用任务台账和独立工作区管理交接
下一轮优化改什么冻结评测口径，优化示范与提示，可比较 DSPy Bootstrapping、MIPROv2 或 GEPA提示优化停滞或需要降低线上延迟时，在相同评测下比较轨迹 SFT、GRPO 或策略蒸馏

如果你对表里密集出现的技术名词还有些陌生，可以按这五步的演进逻辑来理解它们各自解决什么痛点、边界在哪里：

  • 控制流（固定工作流 vs. ReAct 循环）：如果任务步骤能提前写死（比如“先分类、再查库、最后格式化”），用提示串联、路由或并行工作流既便宜又稳定；只有当“下一步该做什么”必须等上一步结果出来才知道时，才引入 ReAct（让模型交替进行“思考—调用工具—观察结果”的自主循环），并且务必设置步数上限，防止模型陷入死循环烧光预算。
  • 检索与工具（MCP、混合检索、重排与多跳检索）：MCP（模型上下文协议）可以理解成工具界的“统一 USB 接口”，先把工具的输入输出规范清楚。查资料时要分清“没查到”还是“排太后”：如果相关文档压根没进候选列表，说明召回不足，可把按字面关键词匹配的 BM25 和按语义匹配的向量检索结合起来，再用 RRF（倒数排名融合）合并两路结果；如果文档已经在候选里但排在后面没被读到，就加一层更精细的打分器（如 ColBERT 或 Cross-Encoder）做重排；只有当一次搜索根本拿不全答案、必须顺着第一份文档里的新线索再查下一份时，才升级到限制最大查询次数的 Agentic RAG。
  • 状态与记忆（日志清理 vs. 压缩与长期记忆）：最稳妥的起点是保留完整的原始事件日志，只把早期特别长的工具返回结果屏蔽掉（减少噪声），同时保持开头的系统提示和前缀不变以便复用推理缓存。只有当单次对话实在塞不进上下文窗口时，才引入结构化压缩（按固定字段提炼历史）；只有当系统确实需要“今天聊完、下周还记得”的跨会话能力时，才去对比 Mem0、MemGPT 或可读写的技能文件。
  • 单 Agent vs. 多 Agent 协作：多 Agent 会带来额外的通信开销和交接出错风险，因此必须先测清楚一个强单 Agent 的质量、成本和耗时作为参照。只有当子任务确实可以同时并行提速，或者不同环节需要严格隔离上下文（防止彼此信息污染）时，才拆分出“协调者 + 多个工作者”，并用任务台账和独立工作区管好交接状态。
  • 系统优化（先调提示，再动权重）：无论怎么优化，第一步都是冻结评测口径（确保前后对比用的是同一把尺子）。低成本的起点是自动化优化少样本示范与提示词，比如用 DSPy Bootstrapping、MIPROv2 或 GEPA 搜索更好的提示组合；只有当提示词调优已经触顶，或者线上需要用更小的模型来降低延迟与成本时，才进入权重级优化——在完全相同的评测集上对比轨迹 SFT（用成功轨迹做监督微调）、GRPO（面向结果奖励的强化学习）或策略蒸馏（把大模型的行为迁移到小模型）。

3. 端到端系统故障诊断树

上一节讲清了如何搭建基线并按证据升级组件；但在真实开发里，系统跑不通往往不是因为“组件不够高级”，而是链路里的某一环悄悄出了差错。本节要解决的问题是：当 Agent 在评测集或线上运行失败时，如何避免凭直觉盲目改提示词，而是沿着清晰的路径由外向内快速定位真正根因。

你可以按照以下五步诊断树逐层排查，每一层都先看客观记录，再下结论：

  1. 检查评测器与环境（Is the Eval Broken?）：先别急着怪模型。打开执行轨迹记录（Transcript），查看当时的用户输入、可见的模型输出、工具调用与回执，确认是不是测试环境没有重置干净、外部依赖接口临时波动，或者负责打分的校验程序（Verifier）写了过于死板的正则断言，把其实答对了的合理方案误判成了失败（即假阴性，False Negative）。
  2. 检查感知与检索层（Did it Find the Right Context?）：如果环境和评测器没问题，就检查模型到底“看没看见”关键信息。先找出回答这道题所需的具体条款或数值，再顺着搜索回执、实际送入模型的文本、最终回答这三份记录逐项核对，看关键证据是在哪一步丢掉的。
  3. 检查工具契约与执行层（Did the Tool Call Succeed?）：检查模型调用外部工具时是否出了协议层故障，例如输出的 JSON 参数被长度上限截断、传入的参数类型与接口要求不匹配，或者工具只返回了一个语焉不详的不透明错误码，导致模型不知道错在哪、在同一条失败命令上反复死循环重试。
  4. 检查长程状态与记忆层（Did Context Drift or Conflict Occur?）：在 10 轮以上的长任务中，重点排查状态是否发生漂移或冲突。例如，上下文压缩（Compaction）生成的摘要是不是不小心丢掉了第 1 轮用户强调的硬约束，或者跨会话记忆模块同时召回了新旧两份相互矛盾的历史数据，让模型无所适从。
  5. 检查安全与人机边界（Did it Violate Policy or Act Without Clarifying?）：最后检查行为边界是否失守。例如，当用户需求本身含糊不清时，Agent 是不是擅自盲目猜测并直接执行，而不是调用 ask_user 先向用户确认；或者是否被外部网页、文档里夹带的间接提示注入（藏在外部数据里的恶意指令）带偏了原本的执行方向。

原课程阅读清单与导读

本讲无新增必读论文。建议结合前十五讲的核心阅读材料，重点复盘以下三篇贯穿全课程方法论的基石文献，分别对应“系统架构思维”“工程化落地模式”与“评测驱动迭代”三条主线：

  • Zaharia et al. "The Shift from Models to Compound AI Systems." BAIR Blog (2024).
    • 导读：从宏观视角解释为什么业界正从“单靠堆大模型”转向“多组件协同的复合 AI 系统”，帮你理解第 2 节把检索、工具、编排和优化拆开权衡的底层逻辑。
  • Schluntz & Zhang. "Building Effective AI Agents." Anthropic (2024).
    • 导读：非常接地气的 Agent 工程实践指南，清晰区分了固定工作流（Workflows）与自主 Agent 的适用边界，重点看文中“从最简方案起步、只在必要时增加复杂度”的实战建议。
  • Grace et al. "Demystifying Evals for AI Agents." Anthropic (2026).
    • 导读：系统拆解如何为多步执行的 Agent 设计可靠评测与防误判校验，建议对照第 3 节的五步诊断树阅读，重点体会如何通过审查 Transcript 来校准评分器与定位根因。

动手练习

  1. 课程项目架构全链路自检：对照本讲的“五步架构选型矩阵”与“端到端故障诊断树”，对你正在构建的课程项目或 HW1/HW2 系统做一次完整的工程体检：
    • （a）组件选型与基线审计：按选型矩阵的五个维度，逐一列出你当前系统中每个核心组件的选型理由，并明确写下它对应的“更简单强基线”是什么；如果某个复杂组件还没有经过与基线的同批样例对比，标记为“待验证假设”。
    • （b）失败轨迹诊断与对照修复：从最近的运行日志中抽取 3 条真实失败轨迹（每条保留完整输入、工具回执与最终输出），按五步诊断树逐层排查并指出最早出错的那一层；随后为每条轨迹写出一个“每次只改一个变量”的修复实验方案，写明改动项、固定不变的条件以及用来判断修复是否生效的验收指标。
