HW2｜构建 Agent 评测体系（Evaluate an Agent）

在 HW1 中，我们扮演的是“系统构建者（Builder）”：围绕课程现成的测试套件与模拟评测框架，从零实现一个办公 Agent。但在真实的工业研发与科研场景里，通常不会有人替你提前写好测试脚本——你必须自己定义什么叫成功，并亲手打造测量系统能力的标尺。

本项实践（对应课程第 10–14 讲的评测工程体系）的核心任务是：给定一个预构建的 Agent 系统（例如你在 HW1 中完成的 Cardinal Energy Agent，或第 05 讲中的日历编排 Agent），为其设计并实现一套严谨、可复现的综合评测套件（Evaluation Suite）。整套评测体系需完整涵盖以下五个核心工程模块：

  1. 用四元组框架（Request、Environment、Stopping Criteria、Scorer）构建评测任务集；
  2. 实现确定性代码评分器（Code-based Graders）；
  3. 设计并校准至少一个大模型裁判（LLM-as-a-Judge Eval）；
  4. 构建支持环境重置与多次独立采样（pass@k / passk）的评测运行底座（Evaluation Harness）；
  5. 开展系统性的错误分析（Error Analysis）与受控验证实验。

1. 锁定被测系统与实验边界

这一步解决什么问题：大模型系统只要改了一个提示词、换了温度参数或升级了模型版本，表现就可能天差地别。如果不先固定“考谁、用什么配置考、哪部分题用来调优、哪部分题用来期末考试”，后续的所有评测分数都会失去可比性。

初学者概念速览：什么是 SUT？ SUT（System Under Test，被测系统） 是软件测试领域的标准术语，指的就是你当前要拿来做实验、打分的那个完整 Agent 系统（包含代码、提示词、模型和工具配置）。

在开始编写评测任务前，第一步是冻结被测对象（System Under Test, SUT）的配置快照，确保所有测量结果建立在严格的控制变量基础之上：

  • 锁定配置快照：记录并固定被测 Agent 的代码版本（Git Commit）、底层主模型与辅助模型标识、采样温度（Temperature）、系统提示词、启用工具集的 Schema 以及默认预算上限（max_turns、context_budget）；
  • 隔离开发集与测试集：划分清晰的开发校准集（Dev Tasks）与独立留出测试集（Held-out Test Tasks）。开发校准集可用于日常调试评分器与优化 Agent，而独立测试集就像“闭卷期末考”，仅用于最终报告测量，避免“对着答案调参数”造成虚高分数。

建议围绕办公助手（邮件、政策文档、终端与本地日历）构建一个包含 15–20 个代表性任务 的评测集，覆盖六个关键能力切片：

  1. 单跳与多跳信息检索：跨多封邮件或长文档合并关键事实；
  2. 版本冲突与时效判断：新旧两版政策并存时识别现行有效条款；
  3. 工具异常与降级恢复：工具返回非零退出码、空结果或权限被用户拒绝后的改道能力；
  4. 模糊需求主动澄清：关键参数缺失时主动调用 ask_user 而非盲目猜测；
  5. 跨会话记忆延续与覆写：在第二轮新会话中准确应用更正后的用户偏好；
  6. 对抗性安全与防注入：抵御外部邮件或文档中植入的间接提示注入与隐私诱导。

2. 使用四元组框架定义评测任务

这一步解决什么问题：如果只写一句模糊的提问（比如“帮我查差旅费”），既没规定初始文件夹里有什么文件，也没说超时多久算失败、怎么算答对，评测结果就无法复现。四元组框架把一道评测题拆成四个明确字段，同时用正反例验证题目本身没有出偏。

初学者概念速览：什么是 Oracle（正例参考解）？ 在评测工程中，Positive Oracle 指的是一份“已知完全正确的标准答案与执行轨迹”。把 Oracle 喂给你的评分器必须 100% 给满分，把故意写错的 Negative Case（反例） 喂给评分器必须 100% 拦下来——这相当于在正式给学生阅卷前，先检查自己的“参考答案和改卷脚本”有没有 Bug。

每一个评测任务都应当定义为结构化的四元组（Request, Environment, Stopping Criteria, Scorer），并配套提供一份可通过验证的参考解（Positive Oracle）与至少一份应当被判失败的反例（Negative Case）：

YAML
id: policy-meal-limit-v2
slice: conflict_resolution
request: "请根据公司现行差旅政策，告诉我国内出差每日餐饮报销上限是多少，并注明所依据的文档编号与生效日期。"
environment:
  fixture_dir: "fixtures/policy_conflict_01"
  files:
    - "DOC-2024-03_Travel_Policy_Legacy.md"   # 旧版：上限 $60/天（已被废止）
    - "DOC-2026-01_Travel_Policy_Current.md"  # 现行：上限 $75/天（自 2026-01-01 起生效）
  enabled_tools: ["search_docs", "read_doc"]
  mode: "auto"
  reset_policy: "每次 Trial 创建全新临时工作区与空会话状态"
stopping_criteria:
  max_turns: 8
  context_budget: 8000
  total_token_budget: 24000
  timeout_seconds: 60
scorer:
  code_checks:
    - type: "substring_present"
      value: "75"
    - type: "tool_called_with"
      tool: "read_doc"
      arg_match: {"doc_id": "DOC-2026-01"}
    - type: "no_file_mutation"
  judge_rubric:
    - id: "correct_current_policy"
      criterion: "回答明确给出了现行每日 $75 的餐饮标准，且未将旧版 $60 标准当作现行标准。"
    - id: "accurate_citation"
      criterion: "回答准确指出了出处为 DOC-2026-01 及其 2026 年生效信息，无任何脱离文档证据的编造。"

设计检查点：逐条核对你的 request 与 scorer 是否严格对齐（1-to-1 Alignment）——确保没有任何一条 code_checks 或 judge_rubric 要求了 request 与 environment 中未曾提供的隐含条件（例如题目没要求写生效日期，评分标准却因为没写日期扣分）。

3. 实现组合评分器并验证“裁判的可靠性”

这一步解决什么问题：评测 Agent 既有客观硬指标（文件有没有生成、命令有没有违规），也有开放语义质量（解释清不清楚、有没有瞎编）。因此需要把“代码硬检查”和“大模型裁判”组合起来，而且必须像校准体重秤一样，先验证大模型裁判本身准不准。

确定性代码评分器（Code-based Graders）

编写确定性检查函数，对每一次 Trial（单次试验）的最终环境状态与事件轨迹（Transcript）进行硬性断言：

  • 状态与产物断言：检查目标文件是否生成、内容/JSON 字段是否合规、只读任务中工作区是否未被意外篡改；
  • 过程证据断言：检查回答引用的文档或邮件 ID 是否确实在 Transcript 的 tool_call 中被成功读取过，检查被拒绝的危险命令是否零执行；
  • 细粒度故障归类：将未通过的 Trial 明确区分为 wrong_answer、missing_citation、policy_violation、max_turns_exceeded、budget_exceeded、malformed_output 或 infra_error，避免将所有失败笼统归为一个布尔值 False，方便后续定位病根。

大模型裁判（LLM-as-a-Judge）与偏差校准

针对开放语义维度，实现结构化的 LLM-as-a-Judge 评分器，并用数据证明它的可信度：

初学者概念速览：什么是 TPR 与 TNR？ 在校准大模型裁判时，我们需要拿人工打分的标准答案做对照： - 真阳性率（TPR, True Positive Rate）：人工判“通过”的样本里，大模型裁判也正确判“通过”的比例（衡量它会不会误杀好答案）； - 真阴性率（TNR, True Negative Rate）：人工判“失败”的样本里，大模型裁判也准确判“失败”的比例（衡量它会不会放过错答案）。

  1. 结构化二元 Rubric 与反编造检查：向 Judge 提供原始任务请求、Agent 最终回复以及从 Transcript 中提取出的工具调用证据摘要。要求 Judge 对每条判据先输出 explanation（引用具体证据）再输出 passed: true/false（先写理由再打分能显著减少草率误判），并独立判定是否存在事实编造（fabricated: true/false）；
  2. 人工一致性校准（Human-Judge Alignment）：在 15–20 条真实或合成的候选回答样本上，先由人工独立标注每条 Rubric 的 PASS/FAIL 金标准，再运行你的 LLM-as-a-Judge，统计裁判的真阳性率（TPR）与真阴性率（TNR）；
  3. 偏差压力测试（Bias Stress Test）：大模型裁判常见两类心理偏差，必须主动测出来：
    • 冗长偏差测试（Verbosity Test）：构造两份事实完全相同的回答（一份精炼准确，一份扩写 3 倍废话但包含一处细微数值错误），检验 Judge 是否会被“字数多、语气专业”的长文迷惑；
    • 位置交换测试（Position Swap Test）：若使用成对比较（Pairwise Judge），交换 (A, B) 与 (B, A) 的展示顺序，统计判罚翻转率（Flip Rate），检验裁判是否偏爱排在前面或后面的选项。

4. 评测运行底座与非确定性统计（pass@k 与 passk）

这一步解决什么问题：大模型具有随机性——同一道题只跑 1 次，答对了可能是运气好，答错了可能是偶发失误。因此评测底座必须支持“每次彻底清空现场、独立重复跑多次”，并用两个互补的统计学指标，同时衡量 Agent 的“上限潜力”和“生产稳定性”。

搭建自动化评测运行脚本，对评测集中的每个任务执行 n 次独立重复试验（例如取 n=5，每次使用不同的缓存盐值 salt 避免命中旧缓存，并彻底重置工作区环境，防止上一次试验留下的文件污染下一次）。

初学者概念速览：pass@k 和 passk 有什么区别？ 假设某道题跑了 n 次，其中成功了 c 次： - pass@k（探索上限）：连续尝试 k 次，至少有 1 次成功的概率。它反映 Agent “有没有能力做出来”（适合评估研究潜力或允许人类重试的场景）； - passk（生产级一致性）：连续尝试 k 次，每一次都全部成功的概率。它反映 Agent “能不能稳定交付”（适合评估无人值守的真实生产环境）。

汇总生成结构化评测报告，包含以下核心指标：

  1. 能力与可靠性双指标：按切片与全局分别计算 k=1,3,5 时的探索上限 pass@k=1−(n−ck)(nk) 与生产级一致性 passk=(ck)(nk)；
  2. 资源与效率分布：统计每个任务的平均模型调用轮数、工具调用次数、输入/输出 Token 数、端到端耗时（P50 / P90，即中位数耗时与 90% 情况下不超过的耗时）与单任务美元成本。

5. 错误归因分析与闭环改进实验

这一步解决什么问题：跑出一张漂亮的分数表不是终点，评测的真正价值是告诉你“系统到底错在哪一步、改什么最有效”。这一步带你走完完整的科学工程闭环：看日志找根因 → 只改一个变量 → 重跑验证效果。

在完成基准测量后，按以下步骤完成闭环分析：

  1. 逐条轨迹复盘与故障树归因（Transcript Inspection & Error Taxonomy）：阅读所有失败 Trial 的完整 Transcript，不要只看最后答错了什么，而要往回翻，找出每条轨迹最早偏离正确轨道的那一步（First Point of Failure）。将其归入检索召回缺失、上下文中间迷失、工具参数错误、过早终止、未主动澄清或评分器自身假阴性等类别，并绘制错误分布统计表；
  2. 单变量受控改进（Controlled Intervention）：针对错误占比最高的一类故障，在被测 Agent 上实施一项有针对性的修改（例如改进某一个工具的描述、优化上下文压缩摘要提示词或增加一步检索重排）。在保持其余所有配置与预算完全不变的前提下重跑评测集，对比改进前后的 pass@1、passk 与成本变化，用数据证明你的改动确实有效。

清晰的目录组织能让评测代码、测试数据、运行原始记录和最终报告各归其位，也方便后续在不重新花钱调模型的情况下，直接对历史轨迹重新打分（Rescore）。

四元组完备性每个任务的 Request、Environment、Stopping Criteria、Scorer 清晰无歧义；正例 Oracle 100% 通过，反例 100% 拦截。
环境隔离与可复现每次 Trial 拥有独立工作目录与缓存盐值，多次运行互不污染；保存完整原始凭证（Full Receipts）支持离线重评。
