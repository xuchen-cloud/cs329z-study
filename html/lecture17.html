第 17 讲｜编程与软件 Agent

如果问过去两年里，AI Agent 在哪个垂直领域率先走出实验室、真正成为全球数百万专业人士每天离不开的生产力工具，答案毫无疑问是软件工程与编程（Coding & Software Engineering）。

为什么软件工程成了 Agent 最理想的突破口？一方面，代码库和命令行终端构成了一个天然数字化、工具完备的环境，Agent 不需要操作物理世界，只靠读写文本和执行命令就能完成绝大多数开发动作。

另一方面，软件工程拥有极其强大的客观可验证反馈信号。代码能不能编译通过、静态类型检查（在不运行程序的前提下，提前核对变量和函数的类型是否匹配）报不报错、单元测试（Unit Tests）（针对单个函数或模块的自动化小测试）和集成测试（检验多个模块拼在一起是否运转正常）能不能跑通，全都有确定性的环境反馈。正是这些客观信号，让 Agent 能够真正跑通“定位问题 → 修改代码 → 运行测试 → 根据报错修正”的自主闭环。

本讲将深入剖析现代编程与软件智能体（Coding & Software Agents）的端到端工作原理：对比三大代表性架构——SWE-agent（开创性的 Agent-计算机接口 ACI）、Claude Code（极简工具与终端原生长程协作）以及 OpenHands（事件流驱动的全栈容器开发平台）；探讨为什么脚手架（Scaffolds）中的每一项细节都是关键的工程决策；结合 SWE-bench 审视四元组评测框架在真实开源仓库修复中的落地；并展望软件开发工程范式的未来演进。

学习目标

  • 理解端到端编程 Agent 从理解需求/Issue、代码库探索定位、编辑修改到运行测试验证的完整工作循环。
  • 深入掌握 Agent-计算机接口（ACI: Agent-Computer Interface） 的设计哲学，对比剖析 SWE-agent、Claude Code 与 OpenHands 三大主流架构的工程权衡。
  • 理解脚手架设计决策（工具粒度、文件编辑格式、终端状态持久性、长程上下文压缩与跨会话进度交接）对编码表现的决定性影响。
  • 掌握 SWE-bench 基准的四元组结构（Request、Environment、Stopping Criteria、Scorer）及其防泄漏与测试验证机制。

知识讲解

1. 从需求到修改和验证

承接导言中“软件工程天然具备客观可验证反馈”的特点，本节我们先聚焦最核心的执行问题：一个编程 Agent 怎样从一条自然语言需求或 Bug 报告出发，独立走完“定位、复现、修改、验证”的闭环？顺着这条工作流，我们再进一步拆解三种主流架构如何为模型设计趁手的工具接口。

端到端 coding agent

早期的代码生成工具（如第一代 GitHub Copilot）本质上是光标处的“自动补全（Autocomplete）”。在这种模式下，人类程序员负责找对文件、定位到具体函数、想好架构，模型只负责顺着光标续写接下来的几行代码。

而一个端到端编程智能体（End-to-End Coding Agent）面对的输入，直接是一个仓库级的自然语言需求或 Bug 报告。例如一条真实的 GitHub Issue：“当传入空的 DataFrame 且设置了 multi_index=True 时，groupby.agg() 抛出 KeyError”。为了独立解决这一问题，Coding Agent 必须自主完成五个紧密衔接的阶段：

  1. 代码库探索与故障定位（Exploration & Localization）：在包含成百上千个文件的陌生代码库中，利用目录浏览、关键词搜索（grep / ripgrep）或符号跳转，找出与 Issue 相关的核心源文件与测试文件。
  2. 故障复现（Reproduction）：编写或运行一段最小复现脚本或测试用例，亲眼观察报错堆栈，确认自己真正抓住了病因，而不是靠猜测盲改。
  3. 代码编辑与补丁生成（Editing & Patching）：在保持原有代码风格与上下文缩进正确的前提下，跨一个或多个文件实施精准修改。
  4. 测试验证与迭代修复（Verification & Iteration）：运行复现测试与相关的回归测试（用来检查新改动有没有把原本正常的功能改坏的存量测试）套件；若测试失败或引入了语法错误，就根据编译器或测试报错信息继续迭代修改。
  5. 生成干净补丁并提交（Submission）：检查 git diff（查看本次修改与原代码之间的逐行差异），确认没有残留临时调试文件或无关改动，输出最终代码补丁（Patch / Pull Request）。

怎样知道自己修到了真正出错的地方？ 我们来看一个教学例子：某报表要求按日期从早到晚排列，输入都是同一年份内有效的“月/日”字符串。用户报告“10/1 排到了 9/30 前面”。

正确的排查顺序不是急着改排序算法，而是分三步推进：先用 10/1 和 9/30 这两个日期重现问题，再顺着数据流追踪日期从读入到排序的变化。如果排序前拿到的仍然是字符串，程序就会按字典序（从左到右逐字符比较编码大小）来排——因为第一个字符 '1' 排在 '9' 前面，所以 "10/1" 反而落在了 "9/30" 前面。定位到根因后，我们可以在生成排序键（Sort Key）时把月和日解析成数字 (10, 1) 和 (9, 30) 参与比较，同时保留原始字符串供界面显示，避免“顺手改格式”引发副作用。

验证哪条约定修复前的观察修复后应看到什么
跨月按时间排序输入 10/1、9/30，输出 10/1、9/30输出 9/30、10/1
已经正确的普通顺序输入 9/12、9/11，输出 9/11、9/12仍输出 9/11、9/12
排序保留原显示格式单条输入 9/1，界面显示 9/1界面仍显示 9/1

判断依据：假如补丁把 9/1 显示成 09/01，即使跨月排序已经通过，第三行仍能指出它改坏了哪条用户可见的约定。

SWE-agent 架构

如果直接把标准的 Linux Bash 终端和 vim 编辑器原封不动地交给大语言模型，会发生什么？实践表明，模型很容易在非交互式管道里调出等待人工按键的交互式命令而卡死；或者用 cat 一次性打印出一万行源码，瞬间撑爆上下文窗口（模型单次调用能装下的最大文本容量）；抑或在用 sed 替换代码时，因为引号转义和行号偏移把整个文件改坏。

普林斯顿大学在 SWE-agent（Yang et al., 2024） 中提出了一个极具洞察力的核心概念——智能体—计算机接口（ACI: Agent-Computer Interface）：

正如人类程序员需要图形界面（GUI）或精心设计的 IDE（人机交互 HCI）才能高效工作一样，以大语言模型为核心的 Agent 也有其独特的感知与认知脾气，需要专门为 LM 量身定制一套 ACI 接口！

SWE-agent 的 ACI 设计体现在三个关键细节上：

  • 带滑动窗口的文件查看器（Windowed File Viewer）：不让模型直接 cat 整个大文件，而是提供 open <path> [<line_number>]、scroll_down、scroll_up。每次只展示约 100 行带行号的代码窗口，并在顶部提示文件总行数与当前所处位置，让模型像翻书一样精准浏览代码。
  • 内置语法检查的受控编辑命令（Linter-gated Edit）：提供 edit <start_line>:<end_line> <<EOF ... EOF。最绝妙的设计在于：每当模型执行一次 edit，ACI 会在底层自动立即运行语法检查器（Linter，如 Python 常用的 flake8，可快速发现拼写、缩进和语法错误）。如果模型这次修改漏了一个冒号或缩进错了一格导致语法错误，ACI 会直接拒绝写入该次修改，并把清晰的语法报错行号立即反馈给模型要求重改。这一机制彻底杜绝了“一步语法改错导致后续十步全面崩溃”的雪崩效应；但也要注意它的能力边界——Linter 只能拦住语法不合法的代码，如果代码语法完全正确、只是把升序写成了降序，仍需要靠运行测试来发现。
  • 精简高信噪比的搜索输出：定制 search_dir 与 find_file，当匹配结果过多时自动提示模型缩小搜索词，而不是把几千条无用匹配全倒进上下文。消融实验（控制底座模型和任务不变、只替换界面组件来做对照测试）证明，在同一底座模型下，精心设计的 ACI 能将 SWE-bench 解决率比原生 Bash 提升数倍。

Claude Code 架构

随着新一代前沿大模型自身对长上下文与原生工具调用的掌握越来越强，Claude Code（Anthropic, 2025） 展示了另一种极具代表性的现代架构哲学——“极简原子工具 + 终端原生协作（Minimalist Tools & Terminal-Native）”：

  1. 克制而正交的工具原语：不堆砌几十个复杂的专用封装命令，而是提供少数高正交性（各工具职责清晰、互不重叠，又能像积木一样自由组合）的核心工具——文件读取（View/Read）、高精度字符串替换编辑（Edit，通过匹配唯一旧代码块替换为新代码块，彻底避免了模型数错行号的问题）、全文件写入（Write）、高速模式搜索（Glob / Grep）以及直接执行测试与构建的 Bash 工具。
  2. 项目级持久指令与记忆（CLAUDE.md）：通过读取代码库根目录或子目录下的 CLAUDE.md 文件，自动加载项目的构建命令、测试运行方式、代码规范与架构约定，省去每次新开对话都重复叮嘱的成本。
  3. 子智能体上下文隔离（Sub-agents for Exploration）：当需要跨大量文件做探索性搜索时，主 Agent 会派生只读子 Agent 去翻找代码，只将精简结论汇回主会话，防止大量中间搜索记录污染主编码上下文，让主会话保持干净聚焦。
  4. 分层权限与人机共驾：文件读取与搜索默认放行，而涉及改动或副作用的文件修改与 Shell 命令执行，则支持按目录、按命令前缀精细配置授权。开发者可以随时在终端里观察 diff、打断引导，或切换至“先规划再执行（Plan Mode）”模式。

OpenHands 架构

作为开源软件工程 Agent 平台的标杆，OpenHands（原 OpenDevin, Wang et al., 2025） 则采用了事件流驱动的客户端—沙箱分离架构（Event-Stream & Sandboxed Runtime Architecture）：

  • 核心中枢是不可变的事件流（Event Stream）：Agent、工具环境（Runtime）与用户界面之间全部通过结构化的 Action（动作）和 Observation（环境观察）事件通信。由于事件按时间顺序追加且不可篡改，事后可以清晰回放“模型做了什么”以及“环境返回了什么”。
  • 全功能持久化容器沙箱：每个会话运行在独立的 Docker 容器（相互隔离的轻量级运行环境，避免误删宿主机文件）中，内部同时集成了持久化的 Bash 终端会话（通过 tmux 保持工作目录与虚拟环境状态）、Jupyter IPython 内核（支持 CodeAct，即让模型直接写并交互式执行 Python 代码块来操控环境）以及无头浏览器（Headless Browser，没有图形窗口但能渲染真实网页，支持前端页面检查与网页查阅）。
  • 多 Agent 委派与卡死检测：支持主 Agent 将特定子任务委派给专职的浏览或验证 Agent，并在运行底座层内置循环检测器，一旦发现模型反复执行相同失败命令就及时介入，防止无限空转。

2. Scaffold、基准与未来

上一节我们对比了 SWE-agent、Claude Code 与 OpenHands 三种风格各异的架构，它们背后其实指向同一个核心工程问题：包裹在模型外层的脚手架（Scaffold）里，究竟哪些设计决策决定了实际成败？弄清设计权衡之后，我们还需要一套严格、可复现的评测基准（SWE-bench）来检验补丁质量，并进一步思考软件工程未来的协作范式。

Scaffolds as design decisions

对比 SWE-agent、Claude Code 与 OpenHands 可以看清一个核心工程事实：包裹在模型外层的脚手架（Scaffold / Harness，即负责工具封装、环境状态管理与循环调度的外层框架）绝不是无关紧要的胶水代码，其中的每一处设计都是直接决定成败的架构决策。

在设计或优化一个 Coding Agent 的 Scaffold 时，工程师需要权衡下面四个问题（Anthropic《Effective Harnesses for Long-Running Agents》, Young, 2025）：

  1. 文件编辑接口怎么设计（Line-based vs. Search-Replace vs. Full Rewrite）？
    • 按行号替换（Line-based）：一旦前面刚改过代码导致行号偏移，模型很容易数错行号并误伤相邻代码。
    • 全文重写（Full Rewrite）：在几千行的大文件上不仅耗时费钱，还容易在输出中途漏掉原本正常的代码。
    • 唯一上下文精确替换（Search-Replace）：要求模型提供足够长且在文件中唯一的原始上下文代码段（Old String），精确替换为新代码段（New String），再配合保存前的自动语法校验，是目前最稳健的工程实践（前提是原文本块必须足够唯一，若文件中出现多处相同片段，接口应明确报错并要求补充更多上下文）。
  2. Shell 状态是否持久？每次开一个独立子进程，实现简单、没有跨步骤副作用，但每次都得重新切换目录和激活虚拟环境；保持持久化 Shell 会话能保留环境变量与工作目录，但必须配合超时与卡死检测机制，防止交互式命令阻塞整个会话。
  3. 测试输出如何防爆窗？运行一次全量 pytest 可能打印出几万行通过日志和几百行报错堆栈，直接塞进上下文会挤掉关键代码。必须对终端输出做智能首尾保留，或采用观察遮蔽（Observation Masking）策略——默认只展示退出码、失败用例与核心堆栈，把完整日志留作按需查询。
  4. 长周期任务如何跨上下文窗口交接（Multi-Window Handover）？当一个大型软件开发任务跨越几十个小时、经历多次上下文窗口重置时，单靠模型记忆是不够的。最佳实践是将角色拆分为两类：
    • 初始化智能体（Initializer Agent）：负责搭建环境、编写功能特性清单 feature_list.json 与进度日志 claude-progress.txt，并完成初始 Git 提交；
    • 增量编码智能体（Coding Agent）：每次新会话启动先读取进度文件与 git log 确认当前状态，每次只专注完成并测试一个原子特性，提交干净的 Git commit 并更新进度文件，让下一轮会话有据可查。

SWE-bench 的四元组

SWE-bench（Jimenez et al., 2024） 用真实开源仓库中的 Issue 来检验 Agent 生成的补丁，SWE-bench Verified 则是其中经过人工核验、确保问题描述清晰且测试用例可靠的精选子集。沿用第 13 讲的四元组评测框架，我们可以清楚区分“Agent 解题时能看到什么”以及“评分器事后如何独立检查”。

四元组组件SWE-bench 中的具体设计
1. Request（请求）来自 GitHub 真实开源仓库（如 django、scikit-learn、sympy）的一条真实 Issue 文本描述（包含用户报告的现象或复现代码，不含对应的 Pull Request 讨论）
2. Environment（环境）从修复前的历史提交（base_commit）和相应依赖开始。实验应隔离真实修复补丁、评分用测试补丁和之后的提交，避免答案泄漏。
3. Stopping Criteria（终止条件）Agent 提交候选补丁（model_patch），或运行达到实验预设的轮数、费用或时间上限。
4. Scorer（评分器）在干净环境中应用候选补丁及评分用测试补丁（test_patch），运行该题指定的两组测试。两组都达到要求，该题才计为解决。

解读基准分数时，一定要留意每道题的测试集究竟覆盖了哪些边界条件。例如，若产品后续还要求正确处理跨年日期，而评测用例仅覆盖同一年，那么即便补丁在基准上拿到满分，跨年处理能力仍需另作验证。SWE-bench 数据字段说明

软件开发的未来问题

随着 Coding Agents 从“解决单个独立 Issue”走向“跨多天自主开发完整系统”，软件工程正面临一系列深刻的开放问题：

  • 从写代码转向写规格与写测试（Spec & Test Engineering）：当生成代码的速度提升十倍时，工程瓶颈迅速转移到了“如何用无歧义的规格说明与严密的测试套件，防止 Agent 引入隐蔽的架构债（为图一时跑通而留下的结构隐患，会让后续修改越来越困难）与安全漏洞”。
  • 代码审查与人类心智模型同步（Code Review & Mental Model）：如果 Agent 一夜之间生成了 5,000 行虽然能跑通测试、但人类工程师从未读过的代码，团队对系统的心智模型（脑中对系统结构与运作方式的清晰认知）就会与真实代码脱节，后续的可维护性与事故责任又该如何界定？设计支持高可读性分解、小步提交与可验证不变量（系统在任何合法操作下都必须始终成立的核心约束）的协作范式，是未来软件 Agent 的核心方向。

原课程阅读清单与导读

  • Yang et al. "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering." NeurIPS (2024). 导读：重点阅读 ACI 的设计原则，留意论文如何通过消融实验，定量对比“带行号滑动窗口 + 自动 Linter 拦截编辑”与原生 Bash 在错误率和定位效率上的差距。
  • Wang et al. "OpenHands: An Open Platform for AI Software Developers." ICLR (2025). 导读：重点理解事件流（Event Stream）与 Docker 沙箱运行时的解耦架构，看看平台如何用同一套 Action/Observation 机制统一调度代码执行、命令行与网页浏览。
  • 拓展阅读：Anthropic. "Claude Code: Best Practices for Agentic Coding." (2025). 导读：适合直接用于日常编码实战。重点掌握 CLAUDE.md 项目上下文配置、“先探索、再规划、后编码验证（Explore, Plan, Code, Commit）”的工作流，以及测试驱动开发（TDD）如何帮 Agent 稳住修改质量。
  • 拓展阅读：Young. "Effective Harnesses for Long-Running Agents." Anthropic (2025). 导读：精读跨多个上下文窗口的长周期编码 Agent 为什么容易“过早宣布完成”或留下半拉子状态，以及如何借助 feature_list.json、进度日志与 Git 提交契约实现可核实的跨会话接力。
  • 拓展阅读：Jimenez et al. "SWE-bench: Can Language Models Resolve Real-World GitHub Issues?" ICLR (2024). 导读：理解 SWE-bench 如何从真实 GitHub 仓库筛选可自动验证的 Issue，以及 FAIL_TO_PASS / PASS_TO_PASS 双重测试门禁如何防止“修好一个 Bug 却弄坏旧功能”。

动手练习

  1. ACI 文件编辑工具对比设计：编写两个供 Agent 修改本地 Python 文件的工具函数：
    • （a）按行号区间替换：edit_by_lines(path, start_line, end_line, new_text)；
    • （b）按唯一原文本块匹配替换：edit_by_match(path, old_str, new_str)，要求先检查 old_str 在文件中是否唯一出现，并在写入后自动调用 ast.parse() 检查 Python 语法合法性（若语法错误则立即回滚原文件并返回具体报错行号）。

    在一个约 200 行的 Python 文件上模拟“连续两次增删代码”的操作（第一次修改会改变后续代码的行号），对比两种方案的出错情况，分析为什么“唯一文本块匹配 + 语法门禁”能显著减少连续编辑事故。

  2. 微型 SWE-bench 任务构造与验证：在一个包含 3 个文件的小型 Python 项目中，亲手植入一个真实的边界条件 Bug（例如除零错误或时区偏移错误），然后按四元组规范构造一套微型基准：编写清晰的 Issue 描述（Request）、一个在修复前必定失败的 FAIL_TO_PASS 单元测试，以及三个覆盖正常路径的存量 PASS_TO_PASS 回归测试。最后让你的 Agent 完整跑通“搜索定位 → 运行测试复现 → 修改代码 → 验证全部测试通过”的闭环，并检查最终 git diff 是否干净无多余调试代码。
