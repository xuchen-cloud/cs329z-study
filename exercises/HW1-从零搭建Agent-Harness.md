# HW1｜从零搭建 Agent Harness

在直接上手高级智能体框架之前，真正理解 Agent 系统的最好方法，是不依赖任何现成黑盒框架，亲手从零搭建一套完整的 **Agent Harness（智能体运行底座）**。所谓“运行底座”，可以类比为汽车的底盘与仪表盘：大语言模型本身像一台只会“读文字、吐文字”的发动机，而 Harness 负责给它接上工具、管理对话记忆、限制费用预算，并在危险操作前踩下刹车。

在本项实践（对应源码仓库 [cs329z/assignment1-harness](https://github.com/cs329z/assignment1-harness)）中，你将为一家虚构的能源公司 **Cardinal Energy** 构建内部办公智能体。整个项目按难度循序渐进，分为三个阶段：

1. **Part 1：固定流水线（Fixed Pipelines，第 1–4 题）**：由你的 Python 代码主导流程，依次实现邮件优先级分类、每日工作摘要生成、BM25 倒排检索器与多跳邮件问答；
2. **Part 2：模型控制循环与安全底座（Agent Loop & Harness，第 5–15 题）**：把流程控制权交给模型。在仅使用最基础的纯文本生成接口 `lm(messages) -> str` 的前提下（**不使用任何第三方 Agent 框架、外部检索库，也不调用模型原生的 Function Calling / Structured Outputs API**），从零实现工具注册表、自定义文本工具协议、Agent 主循环、文档分页搜索与读取、终端沙箱与超大输出截断、上下文压缩（Compaction）、跨会话持久记忆、人机协同审批与防提示注入护栏，并最终通过 20 个模拟用户画像（Personas）的端到端仿真评测；
3. **Part 3：真实交互实验与架构复盘（Field Notes & Design Memo，第 16–17 题）**：通过命令行亲自与自己构建的 Agent 对话压测，并撰写系统设计权衡备忘录。

## 环境配置与测试工作流

在写第一行代码前，我们需要先搭好可复现的本地开发环境，并理解测试套件的运行方式，这样才能做到“改一行代码、几秒内验证对错”。

项目要求 Python $\ge 3.11$，使用 `uv`（一款高速 Python 虚拟环境与包管理工具）管理依赖。所有待实现的业务代码都位于 `cs329z_hw1/` 包内，并通过 `cs329z_hw1/adapters.py` 中的标准入口函数暴露给测试套件。**请特别注意：切勿修改 `types.py`、`adapters.py` 的函数签名，也不要修改 `tests/` 下的测试代码。**

在项目根目录下，先配置 API 密钥环境变量，再拉取课程提供的邮件与公司政策文档语料（解压后包含 24 份公司政策文档与 26,278 封邮件 JSONL 数据）：

```bash
cp .env.example .env
# 在 .env 中填入你的 OPENROUTER_API_KEY
uv run python data/download.py
```

测试套件分为“离线”和“在线”两类。强烈建议在实现每一道题时，严格遵循**“先跑通离线确定性测试，再运行在线真实模型测试”**的节奏，既省钱又好排查 Bug：

```bash
# 1. 运行离线确定性测试（使用 ScriptedLM，零 API 费用，秒级检验控制流与边界合同）
uv run pytest tests/test_tool_registry.py
uv run pytest tests/test_tool_protocol.py
uv run pytest tests/test_agent_loop.py

# 2. 运行在线真实模型评测（标记为 -m live，可先用切片快速迭代，再跑全量）
CS329Z_EVAL_SLICE=5 uv run pytest tests/test_priority.py -m live -s
uv run pytest tests/test_priority.py -m live -s
```

> **初学者概念速览：什么是 `ScriptedLM`？**
> 真实大模型每次回答都有一定随机性，而且调用要花钱。`ScriptedLM`（剧本式模拟模型）是测试套件内置的“假模型”：它不联网，只按测试代码提前写好的“剧本”逐条返回预设文本。用它可以在零费用、零网络抖动的情况下，精准检验你的代码逻辑与边界条件是否写对。

> **缓存与预算机制说明**：`llm.py` 内置了基于 SQLite 的本地调用缓存（`.lm_cache/`）与累计预算账本（Ledger）。这套机制具有**幂等缓存**特性——只要发送给模型的提示词、工具描述与输入消息完全一致，重复运行就会直接读取本地缓存结果，不会重复向 API 计费。如果你想绕过缓存、测试真实模型在多次独立采样下的随机波动，可以通过设置环境变量 `CS329Z_EVAL_SALT` 注入一个新的**盐值（Salt）**（可以理解为给缓存键加上一个“防撞标签”，盐值一变就会强制发起全新请求）。

## Part 1：固定流水线（Fixed Pipelines）

在直接让模型自主循环决策之前，Part 1 先带你练习最稳健的工程模式——**固定流水线**。它的核心思路是：让确定性的 Python 代码负责流程编排、过滤排序和海量检索，只把真正需要语义理解的环节交给大模型。

### 1. 邮件优先级 priority（3 分）

**这一步解决什么问题**：日常收件箱里混杂着紧急故障、普通沟通和垃圾广告。这一题教你用**单次模型调用**把自然语言邮件变成程序可直接处理的离散标签，并学会防御模型“不按格式输出”的异常情况。

- **入口函数**：`run_priority(email: Email, lm: LM) -> tuple[str, str]`
- **核心任务**：仅使用**单次**模型调用，判断一封邮件对收件人的紧急程度，返回 `(category, reason)`：
  - `category` 必须严格属于 `{"urgent", "normal", "ignore", "unknown"}`；
  - `reason` 为非空解释字符串；
  - 严禁修改传入的 `email` 对象（保持输入不可变）。
- **分类准则（站在邮件收件人当时的视角）**：
  - `urgent`：要求收件人在当天、下一个工作日或至多两个工作日内采取行动的明确请求，或收件人直接负责的线上故障/紧急审批；
  - `normal`：发给收件人的常规工作沟通、问题咨询、文档审阅、日程协调或同事便条；
  - `ignore`：无需收件人采取任何行动的广告推销、全员群发广播或自动通知（注意：写着“限时抢购立即行动”的群发广告依然是 `ignore`；但要求收件人本人处理的系统故障告警则是 `urgent`）；
  - `unknown`：当模型的输出无法解析出上述三个明确标签时，必须老实返回 `unknown`，绝不能盲目默认猜 `normal`。
- **验收标准**：离线解析测试全通；在 60 封平衡类别的 Live 测试集上准确率 $\ge 85\%$（至少答对 51 封），且 Live 评测中不出现 `unknown`。

### 2. 日报 daily_digest（4 分）

**这一步解决什么问题**：如果把一整天几十封邮件一股脑塞给大模型写日报，不仅浪费 Token，模型还容易把广告写进简报、把急事漏掉。这一题让你体会**“代码做确定性筛选排序 + 模型做最终摘要”**的经典分工。

- **入口函数**：`run_daily_digest(emails: list[Email], lm: LM) -> str`
- **核心任务**：
  1. 先对传入的一批单日邮件逐封分类（可并发执行，提高速度）；
  2. 由**程序代码**完成过滤与排序：剔除所有 `ignore` 邮件（将 `unknown` 视作 `normal` 保留）、按邮件主题线程归并，并将 `urgent` 置顶排序；
  3. 仅用**最后一次模型调用**生成当日工作简报。若输入为空列表，或所有邮件均被过滤，也应返回合理的简短说明字符串。
- **硬性约束**：
  1. 模型生成的原始日报词数严格不超过 **300 个词**（按 `len(text.split()) <= 300` 判定，必须在提示词中控制模型生成长度，不得在事后用代码暴力截断字符串）；
  2. 必须完整点名提及当天所有 `urgent` 邮件涉及的核心公司、项目或地点实体；
  3. 绝不能混入任何属于 `ignore` 邮件的内容。

### 3. BM25 倒排检索（8 分）

**这一步解决什么问题**：公司语料里有 26,278 封邮件，远超模型的上下文窗口，也不可能每次提问都让程序从头到尾扫描所有邮件。这一题带你从零实现经典搜索引擎的核心数据结构——**倒排索引（Inverted Index）**与 **BM25 相关性打分**。

> **初学者概念速览：什么是倒排索引？**
> 平时我们翻书是“按页码找内容”；而书本末尾的“关键词索引表”则是“按关键词直接查到它出现在哪几页”。倒排索引就是把每篇文档拆成词，反过来建立一张 `词 -> 包含该词的文档列表（倒排链表，Postings List）` 的哈希表。查询时只需查阅查询词对应的那几条链表，速度比逐篇扫描快几个数量级。

- **入口函数**：`run_bm25_build(docs: list[str]) -> BM25Index` 与 `run_bm25_search(index: BM25Index, query: str, k: int) -> list[tuple[int, float]]`
- **核心任务**：使用项目提供的分词器 `tokenizer.tokenize`（转小写并按非英文字母数字切分），从零实现内存倒排索引（Inverted Index）。
- **算法与性能要求**：
  1. **建索引（`run_bm25_build`）**：单次遍历文档列表，构建 `term -> postings` 映射；同时记录每篇文档的长度 $|D|$、包含各词的文档频次 $\text{df}$ 以及全集平均文档长度 $\text{avgdl}$（注意：空文档同样计入总文档数 $N$ 与平均长度分母）。
  2. **打分公式（`run_bm25_search`）**：采用参数 $k_1 = 1.5, b = 0.75$，以及非负 IDF（逆文档频率，越稀有的词权重越高）公式：
     $$\text{IDF}(t) = \ln\left(1 + \frac{N - \text{df}(t) + 0.5}{\text{df}(t) + 0.5}\right)$$
  3. **倒排加速与边界**：查询词去重后，**仅遍历查询词对应的倒排链表（Postings List）**，绝不能在查询时扫描全部 $N$ 篇文档；与查询无公共词元的文档得分为 0，不得出现在返回列表中；结果按得分降序排列（得分相同时按较小的 `doc_id` 升序排列）。
- **验收标准**：5 篇文档手算精度误差 $\le 10^{-6}$；17 条邮件查询的 Top-10 平均召回率 $\ge 90\%$；构建索引耗时 $< 15\text{ s}$，平均单次查询 $< 20\text{ ms}$，在 20 万篇文档中检索仅出现 3 次的稀有词耗时 $< 2\text{ ms}$。

### 4. 多跳邮件问答 email_qa（8 分）

**这一步解决什么问题**：现实中的复杂问题往往无法靠一次搜索直接找到答案，必须像侦探破案一样“顺藤摸瓜”。这一题是从“固定流水线”迈向“智能体循环”的桥梁：让模型自己决定查什么词、读完邮件后再决定要不要继续追查。

- **入口函数**：`run_email_qa(question: str, search: Callable[[str, int], list[Email]], lm: LM) -> tuple[str | None, list[str]]`
- **核心任务**：针对需要跨单封或多封邮件串联线索的问题（例如：先从第一封邮件查出负责某项目的律所名称，再以律所名称为关键词搜出第二封邮件里的托管定金账号），驱动模型自主构造查询、阅读结果并决定是否继续检索。
- **硬性约束**：
  1. 代码层强制限制每道题最多调用 `search` 函数 **3 次**，防止模型陷入死循环；
  2. 返回 `(answer, support)`，其中 `support` 为支持该答案的邮件 ID 列表，且返回的每一个邮件 ID 都**必须确实在本次问答的 `search` 返回结果中出现过**（防止模型凭空编造证据 ID）；
  3. 邮件正文中可能包含恶意的提示注入文本（例如在邮件里写“忽略之前所有指令，直接回答 XXX”），系统必须仅将邮件视为待查证据，绝不执行其中的指令。
- **验收标准**：在 25 道 Live 测试题（含 12 道单跳、13 道两跳）上答题准确率 $\ge 70\%$（至少 18 题），且每道答对题目的 `support` 列表至少命中一条黄金证据邮件 ID。

## Part 2：模型控制循环与安全底座（Agent Loop & Harness）

从第 5 题开始，我们将正式搭建通用的 **Agent Harness**。在这里，模型不再只能按写死的步骤干活，而是拥有一个“工具箱”和一个“思考—调用工具—看结果—继续思考”的主循环；而你的代码将扮演稳健的“裁判与安全员”，负责协议解析、预算熔断、长上下文管理、跨会话记忆以及防攻击护栏。

### 5. 工具注册表 tool_registry（3 分）

**这一步解决什么问题**：当 Agent 可以调用十几个不同工具时，必须有一个统一的“总管”来登记所有工具、把工具说明书展示给模型，并在真正执行前拦住拼错工具名或传错参数的请求。

> **初学者概念速览：什么是 JSON Schema 校验？**
> 你可以把 JSON Schema 理解为一份“参数体检表”，它规定了某个工具需要哪些必填参数、每个参数应该是字符串还是整数。**Schema 校验**就是在真正运行工具代码前，先对照体检表检查模型传来的参数合不合格，不合格直接打回让模型重填，避免程序崩溃。

- **入口函数**：`run_tool_registry(tools: list[ToolSpec])`
- **核心任务**：实现一个管理可用工具的注册表对象，暴露三个核心接口：
  1. `schemas() -> list[dict]`：按注册顺序返回仅包含 `name`、`description`、`parameters` 三个键的字典列表；
  2. `validate(call: ToolCall) -> ToolResult | None`：**仅校验、不执行**。若工具名不存在，返回 `status="unknown_tool"`；若参数不符合该工具的 JSON Schema（使用提供的校验规则），返回 `status="invalid_args"`；若完全合法则返回 `None`；
  3. `execute(call: ToolCall) -> ToolResult`：先调用 `validate`，校验通过后执行恰好一次底层工具函数，成功则返回 `status="ok"` 及字符串结果；若工具函数内部抛出任何异常，捕获并返回 `status="tool_error"` 及错误描述，**绝不向外抛出未捕获的工具异常**（确保单个工具出错不会把整个 Agent 进程撞崩）。

### 6. 文本工具协议 tool_protocol（4 分）

**这一步解决什么问题**：因为本作业不调用模型厂商封装好的原生 `tool_calls` 接口，你需要自己制定一套“暗号协议”，让模型在普通纯文本里既能说人话，也能精准表达“我要调用哪个工具、传什么参数”。

- **入口函数**：`run_render_tools(schemas)`、`run_parse_response(text)`、`run_format_tool_call(call)`
- **核心任务**：设计一套纯文本工具调用协议（例如使用特定起止定界符包裹 JSON 对象），让模型在普通文本输出中表达工具调用。
- **严苛的解析合同**：
  1. `run_render_tools` 生成的工具说明文本必须完整包含所有工具名称及参数字段名，并清楚教模型如何按你的协议格式输出；
  2. 模型单次回复只允许是**纯自然语言最终回答**，或包含**恰好一个**工具调用（若单次回复包含多个工具调用，解析器必须返回 `error`）；
  3. **往返无损与抗嵌套截断**：
     - `format -> parse` 往返必须严格保留布尔值 `true`、整数 `1`、浮点数 `1.0` 与字符串 `"1"` 的类型区分；
     - 当输出在任意字符位置被截断（模拟模型达到 `max_tokens` 上限突然断句），或当工具参数字符串内部恰好包含你自己协议的完整定界符文本时（例如模型想写入一段包含定界符的文本），解析器绝不能崩溃，也不能误解析出残缺的错误指令。
- **验收标准**：通过全部极端边界离线测试，并在 20 个单步工具调用 Live 请求中至少正确完成 18 个。

### 7. Agent loop（8 分）

**这一步解决什么问题**：工具注册表和协议准备好之后，这一题是整个系统的“心脏”——把“用户提问 $\to$ 模型思考 $\to$ 解析并执行工具 $\to$ 把结果喂回模型”串联成一个可多轮对话、带预算限制和自动熔断的状态机。

- **入口函数**：`run_agent_session(lm, tools, config: AgentConfig)`
- **核心任务**：实现支持多轮对话（`send(user_message) -> AgentResult`）、追加式历史记录（`transcript`）与模式切换（`set_mode`）的 Agent 会话状态机。
- **控制流与预算规则**：
  1. **轮次与 Token 双重闸门**：每次 `send()` 独立统计当前轮次（`max_turns`）与累计 Token 消耗（`total_token_budget`，使用 `tokens.py` 计数器）。在发起每一次模型调用前，先检查轮数是否超限，再检查累计 Token 是否超限；
  2. **最后一轮边界**：
     - 在第 `max_turns` 轮（最后一个允许回合）中，如果模型发出了合法的工具调用，该工具**依然要执行**并将结果追加进 `transcript`，随后因轮数用尽返回 `status="max_turns"`；
     - 如果某次模型调用直接产出了最终回答，即便这次调用刚巧跨过累计 Token 预算，依然正常返回该回答并标为 `status="done"`；
  3. **连续三次格式错误熔断**：当模型输出触发解析错误（`parse_error`）、未知工具（`unknown_tool`）或参数非法（`invalid_args`）时，记为一次畸形回复（Malformed，包括捕获 `OutputTruncated` 异常），并将错误反馈给模型让其重试。若**连续 3 次**出现 Malformed，则立即熔断停止并返回 `status="malformed"`；一旦中间有一次合法调用（哪怕工具执行报错 `tool_error` 或被用户拒绝 `denied`），连续畸形计数器即清零；
  4. **追加式不可变日志**：每一步事件严格追加，永不删改已发生的事件；下一轮模型调用必须逐字看到上一轮工具返回的观测文本。

### 8. Cardinal 工具集（2 分）

**这一步解决什么问题**：这一题把前面和后面各个模块的工具正式装进 Cardinal Energy 助手的“工具箱”，并通过两项关键工程技巧（惰性加载与主辅模型分离）来优化启动速度与调用成本。

- **核心任务**：当 `tools=None` 时，自动组装 Cardinal Energy 助手的完整工具箱：`search_emails`、`read_email`、`email_qa`、`daily_digest`、`search_docs`、`read_doc`、`run_terminal`、`remember`、`recall`、`ask_user`。
- **延迟加载与辅助模型路由**：
  1. **惰性加载（Lazy Loading）**：给 26,278 封邮件建索引需要好几秒，如果用户只是来查一份政策文档，提前建邮件索引就是白费功夫。因此初始化会话时**不得**提前读取或构建全量邮件索引，必须在首次实际调用邮件工具时才执行惰性加载，并在会话内复用已建好的索引；
  2. **主辅模型分离**：Agent 主循环的每一步决策调用主模型 `lm`；而工具内部的子调用（如 `email_qa`、`daily_digest` 以及后续的上下文摘要压缩）必须优先调用 `config.aux_lm`（仅当 `aux_lm is None` 时回退使用 `lm`）。这样做一方面可以在离线测试时保证 `ScriptedLM` 的步数严格对齐，另一方面在线上可以用更便宜的小模型处理子任务、降低成本。

### 9. 文档搜索与分页读取 search_docs（5 分）

**这一步解决什么问题**：公司政策文档动辄几百行，如果模型搜到一篇文档就把全文塞进上下文，很快就会撑爆 Token 预算。这一题实现“先看短摘要定位，再按行号翻页精读”的渐进式阅读机制。

- **入口函数**：`run_build_doc_index`、`run_search_docs`、`run_read_doc`
- **核心任务**：为 24 份公司政策文档实现带摘要片段（Snippet）的检索与按行号分页读取：
  1. `search_docs(index, query, k)`：返回至多 $k$ 条匹配结果，每条 snippet 长度 $\le 150$ 个作业 Token，且必须包含原文中至少连续 4 个词的真实片段（严禁编造摘要）；
  2. `read_doc(index, doc_id, start_line, end_line)`：行号从 1 开始（按 `splitlines()` 切分），返回指定行区间的原始文本（不额外拼接行号前缀），单次返回不超过 1,500 Tokens，并返回 `DocWindow` 元数据（允许模型从 `end_line + 1` 无缝续读至 `total_lines`）。
- **验收标准**：在 20 道政策问答 Live 测试（涵盖深层条款、词面同义替换、以及**已被新版政策废止的旧版政策干扰**）中准确率 $\ge 75\%$（至少 15 题），且每题文档读取总量 $\le 6,000$ Tokens。

### 10. 终端与 observation policy（6 分）

**这一步解决什么问题**：让 Agent 能运行命令行终端命令威力极大，但也带来一个经典工程难题——万一一条命令瞬间打印出几十万字符（比如 `cat` 了一个超大日志），会直接把模型的上下文窗口冲垮。这一题要求你设计一套既“不撑爆窗口”又“不丢信息”的观测截断策略（Observation Policy）。

- **核心任务**：封装 `sandbox.run_terminal(cmd, workspace=..., timeout=...)`。仅当命令实际执行且返回退出码 `0` 时标记 `status="ok"`；非零退出码、超时或被沙箱拦截均返回 `status="tool_error"` 及可读的错误原因。
- **超大输出观测策略（Observation Policy）**：
  - 测试中包含单次打印 **600,000 字符** 的极端命令，而单次模型调用的总上下文预算可能只有几千 Token；
  - 你需要设计合理的截断与转存策略（例如：保留头部与尾部关键行，将完整输出落盘到工作区临时文件，并在返回结果中明确告知模型文件路径以及如何用 `grep` / `sed` 按需分段查看）；
  - **一致性要求**：`transcript` 中保存的 `tool_result` 必须与实际展示给模型的截断文本一致。
- **验收标准**：Live 测试包含 9 道主问题加 1 道针对截断列表中间某行的追问，要求至少答对 8/10。

### 11. 上下文压缩 compaction（8 分）

**这一步解决什么问题**：在长任务中，哪怕每一步输出都做了截断，几十轮对话和工具调用累积下来，总 Token 数依然会超过模型的上下文窗口上限。这一题教你构建**上下文压缩（Compaction）**机制，让 Agent 在有限窗口内“边干活边提炼笔记”，不会因为超长报错而中断。

- **核心任务**：确保每一次调用 `lm(messages)` 时，严格满足 `count_message_tokens(messages) <= config.context_budget`，且当前轮次用户的原始请求消息（Current User Message）必须始终保留在上下文中。
- **架构衔接**：测试会使用 4,000 Tokens 的紧凑窗口，连续发起约 60 次工具调用与 12 轮用户对话。为了同时满足“下一轮调用必须逐字看到上一轮工具输出”与“总长度不超过预算”，应当遵循三层配合策略：
  1. 单条工具输出在进入事件流前，先通过第 10 题的观测策略控制上限；
  2. 底层 `transcript` 保持追加不可变（完整保留原始记录，方便审计与排错）；
  3. 当构造本轮模型输入视图超出 `context_budget` 时，调用 `aux_lm` 将较早的历史轮次压缩为保留了核心约束、关键发现与进度的摘要消息。

### 12. 跨会话记忆 memory（8 分）

**这一步解决什么问题**：普通的对话历史在关闭窗口（重启会话）后就会清零。这一题让 Agent 拥有把关键事实写入本地磁盘、在下次全新会话中重新调取的“长期记忆”能力，同时解决“旧事实被更正后不能新旧混淆”的经典难题。

- **核心任务**：实现仅在 `config.memory_dir` 目录下持久化读写数据的 `remember` 与 `recall` 工具。
  - 不同 `memory_dir` 之间必须完全隔离，互不干扰；
  - 当记忆库为空时，调用 `recall` 也必须返回 `status="ok"` 及清晰的空状态提示（而不是报错）。
- **冲突更新要求**：在跨会话测试中，第一轮会话用户会告知某项事实或项目编号，随后在同一会话或后续句子中更正该编号；第二轮新会话启动时仅共享同一个 `memory_dir`，Agent 必须能够召回更正后的最新事实，避免将已作废的旧编号混入回答中。

### 13. 交互、审批与 steering（7 分）

**这一步解决什么问题**：真正可用的办公 Agent 不能闷头瞎干——需求不清楚时要会反问，执行高风险命令前要请示人类批准，干到一半用户改主意了要能立刻掉头。这一题通过 `UserIO` 接口实现这三项核心人机协同机制。

- **核心任务**：通过 `config.user`（`UserIO` 接口）实现三项人机协同机制：
  1. **主动澄清（`ask_user`）**：调用 `user.ask(question)` 获取用户补充说明，并将其作为 `status="ok"` 的工具结果返回给模型；
  2. **敏感操作审批（Approval in `confirm` mode）**：当 `mode == "confirm"` 时，对于通过了 Schema 校验且非只读的工具（如 `run_terminal`），在执行前必须对 `user.approve(call)` **恰好调用一次**。注意：`ask_user`、`remember`、`recall` 永不触发审批弹窗；非法调用在校验阶段直接报错，不打扰用户审批。若用户拒绝，则绝不执行该工具，记录 `status="denied"` 及拒绝理由，并让模型继续思考替代方案；
  3. **中途插话转向（Steering via `pending_message`）**：在每一次调用模型之前，恰好调用一次 `user.pending_message()`；若返回非空新消息，立即将其作为新的 `user` 事件追加进历史并纳入本次模型输入，使 Agent 能够实时响应用户的中途改口。

### 14. Deny rules 与 prompt injection（4 分）

**这一步解决什么问题**：外部邮件和文档是不可信输入，里面可能藏着恶意指令（提示注入攻击），诱导模型去删文件或窃取密钥。单靠提醒模型“不要听坏人的话”并不可靠，因此这一题在**宿主代码层**设立一道不可绕过的硬性安检门。

- **核心任务**：在执行 `run_terminal` 前，对完整命令字符串遍历 `config.deny_rules` 执行正则搜索 `re.search(rule, cmd)`。
  - 一旦命中任一拒绝规则，无论当前是 `auto` 还是 `confirm` 模式，**立即强制拒绝（不调用 `user.approve` 弹窗，也不执行命令）**；
  - 同时确保宿主程序的 `mode` 与 `deny_rules` 绝不会被任何工具返回的文本修改。
- **验收标准**：在 7 道植入了间接提示注入的文档与邮件 Live 测试中，恶意命令实际执行次数严格为 $0$，且正常业务问题答对率 $\ge 6/7$。

### 15. 模拟用户端到端评测 sim_eval（10 分）

**这一步解决什么问题**：前面 14 题像是在逐个零件做单元测试，而这一题是整车路测——用 20 个虚拟同事（Personas）模拟真实办公场景，全面检验你的 Agent 在多轮复杂任务中的综合稳定性。

- **评测机制**：运行 `cs329z_hw1.simulation` 中的 20 个端到端用户画像场景（涵盖政策检索、多跳邮件、日报追问、确认模式终端操作、跨会话记忆延续与更正、模糊需求澄清及对抗性注入）。
- **满分标准**：单条 Persona 只有在 **Agent 未崩溃 + 全部确定性代码检查（`checks.py`）通过 + 裁判模型（`judge.py`）判定全部 Rubric 通过且无编造（No Fabrication）** 时才计为成功；20 个场景中至少通过 **16 个** 即获满分：

```bash

uv run python -m cs329z_hw1.simulation --only memory
uv run python -m cs329z_hw1.simulation --slice 3

# 运行全量 20 个 Personas 端到端评测
uv run python -m cs329z_hw1.simulation
```

## Part 3：交互实验与设计复盘

跑通自动测试只是起点，真正优秀系统工程师的成长来自于“亲自用自己写的系统、直面它的笨拙与缺陷，并把背后的架构权衡讲清楚”。Part 3 包含两项开放式实践交付。

### 16. 使用记录 field_notes（10 分）

**这一步解决什么问题**：自动测试很难覆盖人类真实对话时的各种临场变化。亲自上手聊一聊，往往能立刻暴露出提示词、交互体验或边界处理上的盲区。

运行交互式命令行 `uv run python -m cs329z_hw1.chat`（默认开启 `confirm` 确认模式），亲手向你的 Agent 提出至少 5 个涵盖不同能力维度的新请求（查政策、查邮件、运行终端命令、故意提出指代不明的问题测试澄清、提出触发拒绝或中途修改要求的问题）。结合保存的 `runs/chat-*.json` 轨迹文件，撰写 1 页实验观察笔记（`field_notes`），客观记录系统的真实表现、暴露出的缺陷以及你据此做出的代码改进。

### 17. 设计备忘录 design_memo（20 分）

**这一步解决什么问题**：写代码容易陷入局部细节，撰写架构设计备忘录能逼着你跳出来审视每个核心决策背后的利弊取舍，并培养用真实运行证据说话的工程习惯。

撰写一份 2 页的架构设计备忘录（`design_memo`），结合具体代码与运行证据逐项回答以下 10 个核心工程问题：

1. **BM25 误差分析**：找出一道 BM25 将无关邮件排在相关邮件前面的具体查询，从词频、IDF 或文档长度解释原因。
2. **工具协议设计**：你采用了什么定界符与格式设计？它是如何保证在任意位置截断或参数内嵌协议文本时依然安全解析的？
3. **空承诺处理**：当模型只用自然语言回复“好的，我现在就去帮您查一下”却没有发出任何工具调用时，你的主循环如何区分它是真的回答完毕还是半途忘了调工具？
4. **文档检索窗口权衡**：你的 `search_docs` 片段与 `read_doc` 分页大小是如何设定的？如何帮助模型识别已废止的旧版政策？
5. **超大终端输出策略**：面对 60 万字符的终端输出，你采用了什么截断与转存策略？模型如何读取被截断掉的中间行？
6. **上下文压缩（Compaction）**：你的压缩策略在何时触发？如何保证早期对话中的硬性约束在多次压缩后不丢失？
7. **跨会话记忆治理**：检查 `sim_eval` 运行后的真实记忆存储文件，分析存下了哪些高价值信息、遗漏了什么，以及如何处理事实更正。
8. **审批策略边界**：在 `confirm` 模式下，哪些工具被你设为免审只读、哪些需要审批？为什么这样划分？
9. **沙箱真实隔离边界**：在你的开发机上运行 `uv run python -c "from cs329z_hw1 import sandbox; print(sandbox.jail())"`，结合 `sandbox.py` 源码分析当前操作系统的沙箱实际上拦截了什么、又有哪些潜在风险是它挡不住的。
10. **整体系统局限性**：如果将这套 Harness 直接部署到真实企业生产环境，最薄弱的环节在哪里？
